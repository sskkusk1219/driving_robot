# 要求内容

## 概要

自動走行の車速追従KPI（プライマリーKPI）に大量違反している問題を解消する。preview二重補償の解消（Stage A）、チューニングプロセス改善（Stage B）、反復学習制御ILC導入（Stage C）の3段階で、p95≤0.2km/h / max≤1.0km/h / 符号反転≤1回/5秒窓 の達成を目指す。

## 背景

### KPI違反の実績（session_717e2609, 06_WLTP_ExHi, 2026-07-07 06:34:44, 322秒）

- |偏差| p50=0.48, **p95=1.97km/h**（基準0.2）, **max=3.44km/h**（基準1.0）
- 違反時間 82.4秒（全体の**25.6%**）、違反セグメント36個
- 符号反転: 5秒窓で最大**19回**（基準1回）

### 生ログ解析＋コード調査で特定した根本原因（3層）

1. **preview二重補償（系統誤差の主因）**
   - FFモデル `poly_spec_inverse_lookahead` は特徴量 `dv_0.5〜dv_3.0`（未来Δv）で学習しており、むだ時間補償を構造的に内蔵している
   - にもかかわらず `drive_loop.py:224` が `t_ctrl = elapsed_s + preview_time_s(=0.5s)` で前倒しした基準を**FFとPID両方**に与えている
   - 結果: 実車速が基準を**約0.5秒先行**（ラグ走査でcorr最大は-0.4〜-0.6s）。ランプ2.5〜3.8km/h/s × 0.5s = 1.3〜1.9km/hの系統偏差
   - PIDは前倒し基準を追うため、このズレを「正しい」として能動的に維持（偏差+1.5km/h超でもアクセル平均12.3%を踏み続ける観測と整合）

2. **チューニングがKPI未達のまま収束**
   - 最新学習サイクル(learning_cycles id=1c12ade7)の stage2_best_cost=**643** ≒ ハード違反約6回残り
   - `tuning_cost` の `100×hard違反回数` が不連続で勾配情報がなく、座標降下(14+5runs)が局所解で停滞。preview=0.5は一度も動かず
   - チューニング規定走行(42s/最高112km/h)は本番モード(WLTP_ExHi: 323s/131km/h)と別物で適合結果が転移しない

3. **FF残差＋速度依存プラントゲイン＋固定PID**
   - モデルMAE≒2%（**単位はペダル開度%**、車速km/hではない）は高速域(120-140km/h)の定常ペダル1.7〜2.4%と同オーダー → FF単独では±2km/h級の誤差
   - プラントゲインが速度で大きく変動（60-80km/hで定常アクセル12% vs 120-140km/hで1.7%）するのにPIDは固定ゲイン → 高速域で振動（周期1.1s、振幅std=1.09km/h）
   - 0.5sズレ補正のシミュレーションをしてもp95=1.60残存 = この層だけでKPIの8倍

### 検討済みの結論（ユーザー質問への回答）

- **モデル(MAE/RMSE/R2)**: MAEの単位はペダル開度%。R2=0.90〜0.95はFF初期値として良好だが、FF単独でp95≤0.2km/hは原理的に不可能。モデル作り直しは不要で、閉ループ側で残差を殺す
- **PID**: ゲイン値以前に「preview付き基準を追わされる構造」が誤り。構造修正→ゲインスケジューリング→再チューニングの順で直す
- **追加制御**: 反復学習制御（ILC）。シャシダイナモの同一モード反復走行は再現性が高く、残差を時刻別補正テーブルに蓄積すれば反復再現性のある誤差をほぼゼロにできる

## 実装対象の機能

### 1. Stage A: preview二重補償の解消
- FFはnow-frame基準を受け取る（先読みはモデルのhorizonsが担う）
- previewはPID専用ノブ `pid_preview_s`（既定0.0、上限1.0s）として分離
- 既存DBのJSONBキー `preview_time_s: 0.5` はフィールド改名により読込時に無視され0.0で補完（マイグレーション不要）

### 2. Stage B: チューニングプロセス改善
- tuning_costのハードペナルティ連続化（超過量×時間の積分をKPIMonitorに追加）
- 本番モードの代表区間でチューニング評価走行（`build_tuning_trajectory_from_mode`）
- FFモデル局所勾配によるPIDゲインスケジューリング（速度依存プラントゲインの正規化）

### 3. Stage C: 反復学習制御（ILC）
- 走行ごとの時刻別残差 e_j(t) から補正effortテーブルを学習: u_{j+1}(t) = clip(Q(u_j(t) + L·e_j(t+Δ)), ±amp_limit)
- profile×mode単位でDB永続化（新テーブル ilc_tables）
- drive_loopのeffort合成に組み込み（ff + pid + ilc）
- WebUI: 自動走行画面にILC状態表示・有効/無効・リセット

## 受け入れ条件

### Stage A（実機検証ゲートA）
- [ ] pytest tests/unit 全緑、ruff/mypy通過
- [ ] 実機WLTP_ExHi走行のラグ走査で corr最大ラグが **0±0.1s**（現状-0.4〜-0.6s）
- [ ] max偏差・p95が現状値（3.44 / 1.97）から改善

### Stage B（実機検証ゲートB・中間ゲート）
- [ ] 学習サイクル再実行でコストが段差なく単調減少、4座標（kp/ki/kd/pid_preview_s）全てが初期値から動く
- [ ] WLTP_ExHiフル走行で **max≤1.0（hard違反0）、p95≤0.5、符号反転≤3回/5秒窓**
- [ ] 60-80km/h帯と120-140km/h帯の偏差分散差が解消

### Stage C（最終合格判定）
- [ ] WLTP_ExHiをILC有効で連続5〜8回走行し、kpi_historyでp95/max/reversalの収束を確認
- [ ] **連続2走行で p95≤0.2 / max≤1.0（hard=0） / 符号反転≤1回/5秒窓 を全て満足**
- [ ] 停止移行区間（走行終盤）の+1〜3.4km/h違反もILC補正で吸収
- [ ] ILCリセット後1走行目（補正なし）でもStage Bゲート（max≤1.0）を維持

## 成功指標

- プライマリーKPI 3項目の完全達成（上記Stage C判定）
- 各Stageが独立にデプロイ・実機検証可能（A→B→C直列、Stageごとにゲート判定してから次へ）

## スコープ外

- FFモデルのアルゴリズム変更（Ridge→他モデル等）。現行モデルはFF初期値として十分
- KPIしきい値自体の変更
- ボタンサーボ/タイムスケジュール関連（別機能）
- 学習運転パターンの変更（**B-7で条項改訂**: B-6'実機結果を受け、CRUISE_TRIM追加=B-7-2 と予測的cap離脱=B-7-5 の範囲に限り変更する。125-140km/h×微小開度のデータ欠損と最高車速オーバー156km/hが実測されたため）
