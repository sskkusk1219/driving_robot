# 研究走行の解析（research-run-analysis）

`tests.research.main --steps 1,3` が残す走行 CSV を、ProblemReport の実機確認で毎回やってきた形で解析する。
スクリプトは `scripts/` にあり、毎回書き直さずに使う。書き直すたびに数え方が少しずつ変わり、前の報告と
数字が合わなくなる（実際に「短いオフ」の数え方がずれかけた）ので、同じ物差しを使い続けることに意味がある。

## 前提

- リポジトリの直下で `.venv/bin/python .claude/skills/research-run-analysis/scripts/<名前>.py …` と実行する（pandas・matplotlib は分析専用で入っている。src/tests のコードからは import しない）
- 走行の指定は `ラベル:トークン`（例 `6e:130454`）かトークンだけ。トークンは `20261109_130454`・`130454`・CSV のパス。スタブは `stub:125814`
- 走行時の設定は CSV と同じ名前の `.yaml`（main が保存する）から読む。min の開度・KPI の設定・計画の作り方はその走行のもの
- 偏差 ＝ 実車速 − 基準（正 ＝ 速すぎ）。時刻は JST（CSV 名も JST）
- 研究系の設定は走行ログの列には残らない。どの設定で走ったかは `.yaml` と、走行ログ（`<scratchpad>/run*.log`）の「C12 handover」などの要約行で確かめる

## 道具と使いどころ

| スクリプト | 何を出すか | 使う場面 |
|---|---|---|
| `kpi_table.py` | 走行ごとの 最大・p95・\|偏差\|>0.5 / >1 秒・往復 全体 / 60 s 最大（レポート 5 章と同じ定義）・1 秒未満のアクセルのオフ（`--offs` で時刻と原因） | 結果の表の最初の 1 枚 |
| `episodes.py` | \|偏差\|>0.5 の場面を走行ごとに列挙し、直前 3 s に立っていた印の列（coast_handover・play_floor_active・hold_scene…）を付け、最後に「場面 × 走行」の表 | 悪化が新しい仕組みのせいか、前からある場面か（日のばらつき）を分ける |
| `window.py` | 時刻の窓の中の列の表（`--preset base/coast/dob/stop/launch/all`、`--cols +列`） | 1 場面を数字で読む。何が開度を動かしたか（c10・dob・coast の分）を見る |
| `reversal_windows.py` | 2 本で往復がどの 60 s 窓で増えたか・その窓で仕組みの印が立っていた秒数・KPI の全体値 | 往復の KPI が悪化したときの出どころ探し |
| `plot_scenes.py` | 場面ごとの比較図 PNG（列 ＝ 場面、行 ＝ 走行。各走行は偏差＋ペダル実開度、`--cmd` で指令も） | ユーザーへの報告。数字より形で伝わる |
| `plan_at.py` | 実行時と同じ作り方の計画（effort・要る加速度・行の印）。走行のトークンを渡すとログの FF と突き合わせて再現できているか先に出す。`--set key=val` で案の机上比較 | 「計画がそうなっているのか、FB がそうしたのか」を分ける。机上の見込み |
| `make_run_yaml.py` | 本体 yaml から走行用コピーを作る（`--set`・モード W/U/US06/AMA・chmod a-w・本体との差を表示） | 実機・スタブ走行の前 |

`plan_at.py` は計画を 1 回作るのに約 1 分かかる（`--set` があると 2 回）。Bash の timeout を 300000 にするか run_in_background で回す。

## いつもの流れ（実機 3 本の結果を報告するとき）

1. **表**: `kpi_table.py 前:… 後:… …`（モードごとに 前 → 後 を並べる）。比べる相手は同じ日の走行を優先する（低速の偏り・往復は日や時間帯で動く）
2. **場面**: `episodes.py 前:… 後:…` をモードごとに。片方にしか無い場面・大きくなった場面だけ拾い、直前に新しい仕組みの印が立っていたかを見る。立っていなければ「この仕組みのせいではない（推測: 日のばらつき）」と書ける
3. **往復が増えたら**: `reversal_windows.py 前 後`。増えた窓で印が 0 秒なら、その仕組みは原因ではない
4. **狙いの場面を数字で**: `window.py 前 後 t0 t1 --preset coast` など
5. **図**: `plot_scenes.py` で狙いの場面（直したかった所）と、悪化した場面を 2〜3 列。出力は scratchpad に置き、`SendUserFile` で送る（caption に「上段 前・下段 後、左 … 中 … 右 …」）。送る前に Read で画像を見て、軸・凡例・題が読めるか確かめる
6. **計画か FB か**: 計画の行の印（惰行の埋め・先置き…）が要るときは `plan_at.py <走行> t0 t1`

報告では数字に CSV 名（時刻）を付け、「推測」は推測と書く。サマリの数字だけで「直った」と言わず、`window.py` か図で生の動きを見てから言う。

## 図の作法（plot_scenes.py が守っていること）

- 1 つの図に 1 つの縦軸。偏差とペダル開度は別の段にする（2 軸にしない）
- 色は アクセル 青 `#2a78d6`・ブレーキ 橙 `#eb6834`・偏差 黒。点線は 偏差 ±0.5 と開度 min
- 題に「ラベル（時刻）　場面」。上の注記に、各列が何の場面かを書く（`--note`）
- 日本語フォントは BIZ UDPGothic（無ければ文字が豆腐になる → `fc-list | grep -i gothic` で確かめる）

## 走行用 yaml（make_run_yaml.py）の注意

- 必ず本体から作る。前のコピーから作ると、決定と違う値が残って分析がぶれる
- `--set` のキーは yaml の中で 1 回だけ出る名前。0 回・2 回以上はエラーで止める（同名キーの書き換え事故防止）
- 走行を任せるサブエージェントには「yaml は読むだけ」と伝える。コピーは読み取り専用にしてある
- 走行が終わったら、ログのモード名と走行時間が yaml のモードと合っているか確かめる

## 数え方の定義（前の報告と比べるとき）

- 往復: `kpi.chatter_metrics`（山・谷から 0.1% 戻ったら 1 回、アクセルを操作している時間で割る、60 s 窓の最大）。走行レポート（report*.md）とは ±0.01 ずれることがある（原因は確かめていない。0.01 の差は判断に使わない）
- 1 秒未満のアクセルのオフ: 実開度が min ＋ 0.8% 未満へ落ちて 1 秒未満で戻った回数。原因は落ちる直前 0.6 s で指令がいちばん落ちた行で「C12 の離し」「C10 が min へ」「計画の短い惰行」に分ける
- 場面: \|偏差\| > 0.5 の行が 1.5 s 以内に続くまとまり。走行どうしは開始時刻が 3 s 以内なら同じ場面
