# ProblemReport の作成・更新（problem-report）

driving_robot で見つかった問題を「議論 → 決定 → 段ごとに実装・確認 → クローズ」まで 1 ファイルで追える形に記録するスキル。
読み手は 2 人: 後で読み返す**ユーザー**と、引き継いで作業を続ける**次のセッションの Claude**。どちらにとっても、
今どこまで進んだか・何を根拠に決めたかが、ファイルを開いた瞬間に分かることを目指す。

`docs/Problem/ProblemReport_20260925.md` が良い例（全体計画の表と進捗ログが特に分かりやすいと評価された）。
ただし段の結果・実行手順の置き場所は、このスキルの形（段ごとにまとめる）に合わせて改善している。

## 章立て（この順で固定）

| 章 | 書くこと |
|---|---|
| `# YYYYMMDD <何をどうするか一言>` | タイトル。ファイル名の日付と一致させる |
| 概要 | `**状態: 進行中（段N 〜待ち）**` または `**状態: クローズ（YYYY-MM-DD）**`。続けて 2〜3 行で、何が問題か・今どこまで進んだか・結論と根拠ファイル名 |
| `## 問題` | 現象と、なぜ困るか。数行で十分 |
| `## 議論で確認した事実` | 表 `項目 \| 内容`。実測値には出典（CSV 名・pkl 名）を添える。推測は「推測」と明記する |
| `## 検討した案` | 表 `案 \| 内容 \| 判断`。採用案は太字＋「（採用）」、不採用案は理由を書く |
| `## ユーザー決定（YYYY-MM-DD）` | 計画時にユーザーが決めた方針だけ。段の途中で出た決定はその段の中に書く（後述） |
| `## 全体計画` | 計画ファイルのパス、進め方 1 行、段の表（下記） |
| `## 各段の内容` | `### 段N: <タイトル>` を段番号順に並べる（後述） |
| `## 進捗ログ` | 表 `日付 \| 内容`。時系列で下へ追記していく |

なぜこの順か: 概要から問題・事実・案・決定までは「なぜこの計画になったか」を説明する部分、全体計画から下は「今それをどう進めているか」を追う部分。
読み手は大抵後者だけを見るので、後者を下にまとめておくと毎回同じ場所（全体計画の表）から入れる。

## 全体計画の表のルール

```
| 段 | 内容 | 走行 | 状態 |
|---|---|---|---|
| 0 | 本ドキュメント作成 | なし | ✅ 完了 |
| 1 | <内容> | なし（オフライン） | ⬜ 未着手 |
```

- 段0 は必ず「本ドキュメント作成」
- 走行列は「なし（オフライン）」「スタブ」「実機（手順2 ×1、手順3 ×2 など回数）」のどれかで、何を確認するのに実機が要るかが一目で分かるようにする
- 状態は 4 種類で統一する: `⬜ 未着手` / `🔄 進行中` / `⏸ ユーザー確認待ち` / `✅ 完了（一言の結論。誰の判断か・日付）`。
  「完了」は結論を書かないと、後で読んだときに何が決まったのか全体計画からは分からなくなる
- 途中で段が増えたら `4b`・`5b`・`6a`〜`6d` のように既存の番号への枝番にする。番号を振り直さない（後から見たときに実行済みログや会話履歴の段番号とずれない）

## 各段の内容（`### 段N: <タイトル>`）

段が進むたびに、その段の見出しの下へ**すべて**まとめる。実行手順を別の章に、結果を末尾に離して書かない
（20260925 はこれをやっていて、段が増えるほど「この段の結果はどこに書いたか」を探す必要が出た）。

小見出しは必要なものだけを使う（順番は次の通り。無いものは省く）:

1. **内容** — 何を変える・変えたか。変更ファイル・関数名・設計上の決定
2. **調整値**（新しい定数・しきい値を入れたときだけ）— 表 `値 \| 現在 \| データの根拠 \| 何に効くか \| いつ決めるか`。
   「データ由来」「仮の値（根拠なし）」「半分データ由来」のどれかを明記する。理由: 後で値を疑うときに、
   実測で決めた値なのか当てはめの都合の値なのかが分からないと、直すべきかの判断ができない
3. **実行手順**（ユーザーが実機/実行する場合）— bash コードブロック＋「見るもの」の説明＋既知の失敗（この段と無関係な既存の失敗があれば明記）
4. **結果**（Claude 確認 YYYY-MM-DD）— 単体テスト件数・ruff・スタブ結果・実機結果。数値には CSV 名など出典をつける
5. **見つかった問題**（実機で不具合が出た段）— 表 `# \| 問題 \| 実測`
6. **決定**（ユーザー YYYY-MM-DD）— その段の中でユーザーが決めたこと

実機で不具合が見つかって直す段（20260925 の 7c・7d に相当）は、この順で書く: **症状（ユーザー報告）→ 原因（CSV 等の生データで確認）→ 修正 → 確認**。
「直った」は生データを見て確かめてから書く（自己選択した閾値のサマリだけで言い切らない）。

## 進捗ログのルール

1 行 = 「何をした・結果（数値 1〜2 個）・次は誰が何をするか（ユーザー確認待ち、等）」。
下に追記していく（最新が最後）。クローズした日の行は太字にする。

例:
```
| 2026-09-27 | 段6d 手順2 実機（065502）を検証: 網羅 穴3セル16s、0.4G超え0行。ユーザー判断で手順3へ |
| 2026-09-28 | **段7d 実機（062254/070218）: KPI悪化なし（ユーザー判断）→ 本問題クローズ** |
```

## 書き方のルール（理由つき）

- **説明の順番**: 用語の定義 → 実測値 → なぜ → 何が困るか。専門用語をいきなり積み上げると差し戻される
- **数値には出典**をつける（CSV 名・pkl 名）。「解決した」と書く前に、自己選択した閾値のサマリだけでなく生データを確認する
- **調整値は最初から根拠を書く**: データ由来か仮値か、何に効くか、いつ決め直すか。後から「この値は何で決めた？」と聞かれて困らないようにする
- **誰が決めたかを区別する**: 「ユーザー決定（日付）」と「Claude 確認（日付）」は別物。オフラインの模擬（スタブ）の点数だけで「採用しない」と結論づけない。
  採否は実機比較で決め、スタブの結果には「数値は判断しない」と添える
- **時刻は JST** で書く。CSV 名は JST・pkl 名は UTC で、日付が 1 日ずれることがあるので注意する
- **選択肢を聞くときは、選択肢の説明文に別の決定を紛れ込ませない**（AskUserQuestion 等で確認する場合）

## 作成・更新・クローズの流れ

### 新規作成

1. `docs/Problem/ProblemReport_YYYYMMDD.md` を `template.md` から作る（同じ日に 2 本目が要る場合は `_2` を付ける）
2. **議論の段階では「問題」「議論で確認した事実」「検討した案」までを書く**。CLAUDE.md の「議論したい」ルールに従い、
   いきなり実行計画を作らず、ドキュメントやコードを参照して深掘りしてから案を出す
3. ユーザーが方針を決めたら「ユーザー決定」「全体計画」を書く（全体計画の計画ファイルは Plan Mode で別に作る）

### 更新（段が進むたび）

**次の 4 か所を同時に更新する**。1 か所だけ更新すると、表と進捗ログが食い違ってどれが最新か分からなくなる:

1. 概要の状態行（進行中の段番号を更新）
2. 全体計画の表のその段の状態
3. その段の「## 各段の内容」の中身（実行手順・結果・決定を追記）
4. 進捗ログに 1 行追記

### クローズ

1. 概要を `**状態: クローズ（YYYY-MM-DD）**` にし、結論と根拠ファイル名を書く
2. 全体計画の表の最終段を `✅ 完了` にする
3. 進捗ログに太字でクローズの行を追記

## テンプレート

新規作成時は `template.md` をコピーして使う。
