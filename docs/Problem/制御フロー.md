## 0. このドキュメントの目的と使い方

`docs/Problem/引き継ぎ20260909.md` のとおり、プライマリー KPI 3 つがすべて未達である。

| プライマリー KPI（PRD `docs/product-requirements.md:64-66`） | 上限 | 第3ラウンド実測 |
|---|---|---|
| 車速追従精度（通常）: \|偏差\| p95 | ≤ 0.4 km/h | 1.42 |
| 車速追従精度（最大逸脱）: \|偏差\| max（例外なし） | ≤ 1.0 km/h | 4.06 |
| 振動抑制: 符号反転（±0.3km/h 往復） | ≤ 1 回 / 5s 窓 | 7〜8 |

本書は**その原因を制御フローの構造から特定するために、`src/` の実装だけを根拠に**
車速追従の全経路を MECE に分解したものである。走行ログの解析結果は
`report20260908/09/09_2.md` に、次ラウンドの方針は `引き継ぎ20260909.md` にあり、
本書はそれらの「実装側の対応物」にあたる。

**読み方**: 1〜5 章が制御フローの記述（What/How）、6 章が全段まとめ表、
7 章が KPI 計測の定義、8 章が**構造的要因の特定**（Why）である。
原因だけ知りたい場合は 6 章の表 → 8 章へ進めばよい。

**MECE の分割軸**は 2 段階で取る。

1. **時間スケールで 4 層に分ける**（層間に重複なし・全経路を網羅）
   走行前オフライン → 走行中 50ms → 走行後エピソード → 学習サイクル
2. **走行中 50ms 層は「effort が通る段」で分ける**（6 章の表がその全リスト）
   基準速度 → プラン → トリム → フェーズ権限 → 不感帯昇格 → 調停 → 開度 → 位置 → 軸

                          │ →VERIFY→PLAN_LEARN→REFINE_FINAL               │

| 層4 学習サイクル | 1 サイクル（約 20 分） | プロファイル・全ログ | FF モデル・PID ゲイン・車両定数・収束プラン | `src/app/learning_cycle.py` |

### 1-3. 制御構成の一言まとめ

**プラン（フィードフォワード） + トリム（フィードバック）の 2 層合成**である。
第2ラウンドまでの「FF + PID + ILC の 3 独立層」は廃止され、反復学習はプラン更新則へ
吸収された（`drive_loop.py` docstring）。

```
   effort = plan.effort_at(t + lead)  +  trim.update(ref, actual)
            └──── 名目値（走行前に確定）───┘  └── 閉ループ補正（3 層切替）──┘
                              │
                              ▼
              フェーズ権限クランプ → 不感帯昇格 → PedalArbiter → 開度
```

`effort` は**符号付き努力量 [%]**（+: アクセル開度、−: ブレーキ開度）で統一されており、
アクセル／ブレーキへの写像は `PedalArbiter` だけが行う（同時踏みが構造的に発生しない）。

## 2. 層2: 走行前オフライン計画（`PedalPlanner.build`）

走行開始時に一度だけ、基準軌跡全体に対する「どこで踏み、どこで抜き、どこで踏むか」の
骨格を作る。`src/domain/control/pedal_plan.py:370-430`。

### 2-1. 生成パイプライン（6 段）

```
 基準軌跡 mode.reference_speed
   │  ① 0.1s グリッドへ線形補間                        grid_v
   ▼
 ② required_accel: np.gradient → 幅 1.0s のセンタリング移動平均   a_req
   │                                    ★非因果（前後 ±0.5s ににじむ）
   ├──────────────┬───────────────────────┐
   ▼              ▼                       ▼
 ③ classify_phases   ④ FF モデル推論     ⑤ analytic_efforts
   a_req vs a_coast(v)  predict_effort()    (a_req − a_coast)/k'(v) + 不感帯
   ±0.15 マージン       （高開度側が有効）   （低開度側が有効）
   │                    └──── blend_model_and_analytic ────┘
   ▼                                  │ |解析値| 5%以下→解析100% / 15%以上→モデル100%
 merge_micro_phases（1.0s 未満を吸収）   ▼
   │                          ⑥ zero_phase_lowpass(1.0Hz)
   │                             ★非因果（前後 ±0.16s ににじむ）
   └────────────┬─────────────────┘
                ▼
       clamp_effort_by_phase  DRIVE≥0 / BRAKE≤0 / COAST=0 / STOP_HOLD=−24%
                ▼
       snap_efforts_to_deadband  |e|<db/2 → 0, それ以外 → ±max(db, |e|)
                ▼
              PedalPlan（efforts[], phases[], dt=0.1s）
```

### 2-2. パイプライン各段の定数と実値

| 段 | 関数 | 定数 | 現行値 | 性質 |
|---|---|---|---|---|
| ① グリッド | `PedalPlanner.build` | `PLAN_DT_S` | 0.1 s | — |
| ② 必要加速度 | `required_accel` | `PLAN_ACCEL_SMOOTH_S` | **1.0 s** | **センタリング窓＝非因果 ±0.5s** |
| ③ フェーズ分類 | `classify_phases` | `PHASE_MARGIN_KMHS` | 0.15 km/h/s | 惰行帯のヒステリシス |
| ③' 微小吸収 | `merge_micro_phases` | `MIN_PHASE_S` | 1.0 s | 短フェーズを隣接へ吸収 |
| ④ モデル | `FeedforwardController.predict_effort` | 先読み 0.5/1.0/2.0/3.0s, 過去 0.5/1.0s | — | Ridge 逆モデル |
| ⑤ 解析値 | `analytic_efforts` | `ANALYTIC_BLEND_LO/HI_PCT` | 5.0 / 15.0 % | 低開度域をモデル外挿から救う |
| ⑥ 平滑 | `zero_phase_lowpass` | `PLAN_LOWPASS_HZ` | **1.0 Hz** | **ゼロ位相＝非因果 RC 0.16s** |
| ⑦ 権限 | `clamp_effort_by_phase` | `stop_brake_opening_pct` | 24.0 % | STOP_HOLD の保持制動 |
| ⑧ 量子化 | `snap_efforts_to_deadband` | `brake_deadband_pct` / `accel_deadband_pct` | **5.0 / 0.5 %** | アービタと同一規則 |

### 2-3. フェーズ分類の判定式

```
  a_coast(v) = +creep_rate            (v < creep_speed = 4.94 km/h)
             = −coast_decel_at(v)     (それ以外、速度依存カーブを補間)

  a_req > a_coast + 0.15  →  DRIVE
  a_req < a_coast − 0.15  →  BRAKE
  それ以外                →  COAST
  v < 0.5 km/h            →  STOP_HOLD（最優先）
```

`000_sample` の惰行減速カーブ（正値 [km/h/s]、`coast_decel_kmhs`）:

| v [km/h] | 5 | 15 | 25 | 35 | 45 | 55 | 65 | 75 | 85 | 95以上 |
|---|---|---|---|---|---|---|---|---|---|---|
| 惰行減速 | 1.60 | 1.70 | 2.57 | 3.18 | **3.63** | 3.62 | 3.25 | 2.56 | 1.65 | 1.60 |

**この曲線は「どこからが BRAKE か」を決める基準線であり、同時に `analytic_efforts` の
原点でもある。** 45 km/h で +2.0 km/h/s を出すのに必要な開度は
`(2.0 + 3.63) / 0.334 = 16.9 %` になる（`k'_accel(45)=0.334`）。

## 3. 層1: リアルタイム制御ループ（`DriveLoop._execute_one_cycle`）

50ms ごとに次の 12 ステップを実行する。`src/domain/control/drive_loop.py:360-627`。

### 3-1. 1 サイクルのフロー

```
 [1] elapsed_s = loop.time() − started_at      （一時停止中は凍結値）
      │  elapsed_s ≥ total_duration → 末端 1 行ログ → 完了
      ▼
 [2] 基準速度を 3 つの時間フレームで引く（3-2 節）
      ref_speed        = ref(elapsed)                    ← KPI・ログ・逸脱判定
      future/past      = ref(elapsed ± horizons)         ← FF・向き判定
      ref_speed_pid    = ref(elapsed + pid_preview_s=0)  ← トリム（= now と同一）
      ▼
 [3] actual_speed = await can_reader.read_speed()        ← 失敗で非常停止
      ▼
 [4] dt = now − last_cycle_time（実測）
      (ref_fb, act_fb) = 1次LPF(τ=0.25s) を ref/実車速の**両方**へ
      ▼
 [5] ゲイン決定（3-3 節）
      is_accel_side = (ref(t+0.5s) − ref(t)) ≥ −0.1
      gain_scale    = min( clamp(g(v)/g_nominal, 0.5, 1.5),   ← FF モデル局所勾配
                           robust_kp_at(v,θ,side)/kp )        ← SIMC ロバスト上限
      fast_kp_eff   = kp × gain_scale
      ▼
 [6] プラン参照（プランあり経路）
      plan_t      = elapsed_s + plan_lead_s(= min(0.4θ, 0.5) = 0.42s)
      base_effort = plan.effort_at(plan_t)
      phase       = plan.phase_at(plan_t)
      phase 変化 → trim.notify_phase_change()（積分・トリム出力を 0 に）
      ▼
 [7] trim_u = trim.update(ref_fb, act_fb, dt, phase, sat, gain_scale, fast_kp_eff)
      ▼
 [8] effort, clamp_hi, clamp_lo = _apply_phase_authority(base_effort, trim_u, phase)
      ▼
 [9] effort = _apply_min_effective_brake(effort, actual, ref_pid, phase)
      ▼
 [10] arb = arbiter.arbitrate(effort, dt) → (accel_opening, brake_opening) 排他
      saturated_high/low = arb の飽和 or 権限クランプ         ← 次サイクルの積分停止へ
      ▼
 [11] pos = opening_to_position(...) → 両軸へ gather 書込 → 電流読取
      過電流 → 非常停止
      ▼
 [12] KPI 集計（**生の ref/actual で全サンプル**）→ 逸脱判定 → 2 サイクルに 1 回ログ
```

### 3-2. 基準速度の 3 つの時間フレーム（重要）

同じ基準軌跡を **3 つの異なる時刻**で引いており、これが位相の要になっている。

| フレーム | 参照時刻 | 現行の前倒し量 | 用途 | 実装 |
|---|---|---|---|---|
| now-frame | `elapsed` | 0 | KPI・逸脱判定・ログ・WS 表示・向き判定 | `drive_loop.py:384` |
| PID フレーム | `elapsed + pid_preview_s` | **0.00 s**（プロファイル値 0.0） | トリムの基準速度 | `drive_loop.py:389` |
| プランフレーム | `elapsed + plan_lead_s` | **0.42 s**（= min(0.4×1.05, 0.5)） | プラン effort・プランフェーズ | `drive_loop.py:433` |

- `pid_preview_s` は意図的に 0（前倒しするとランプ追従中に定常偏差を作るため。
  閉ループ模擬で p95 1.13 → 3.67 と悪化）。
- `plan_lead_s` は **θ に比例**する。θ=1.05s の現プロファイルでは 0.42s（上限 0.5s に未達）。
- **effort と phase を同じ量シフト**している（片方だけずらすと権限クランプが向きを誤る）。

### 3-3. トリム（フィードバック）3 層

`src/domain/control/trim.py`。偏差の大きさで 3 層を切り替える。

```
        |偏差|
          │
  0.1 ────┼──── 凍結帯: 出力を保持し積分も止める（ペダルを動かさない）
          │
          │     低速トリム: 速度形 PI
          │       Δout = slow_kp·Δe + slow_ki·e·dt
          │       slow_kp = 1.0 × fast_kp_eff       (TRIM_SLOW_KP_RATIO)
          │       slow_ki = slow_kp / 1.667         (TRIM_SLOW_TI_S)
          │       レート制限 3 %/s・量子化 0.25 %
  0.3 ────┤ ← FAST_RELEASE（下降時にここを切るまで速い層を維持）
  0.5 ────┼──── FAST_ENGAGE（上昇時にここで速い層へ）
          │
          │     速い補正層: プロファイル PID × gain_scale
          │       out = gain_scale·(kp·e + ki·∫e + kd·ė_filt)、|out| ≤ 50 %
          ▼     ★ この層だけがフェーズ権限を無視できる（max≤1.0 の安全網）
```

| 定数 | 値 | 意味 |
|---|---|---|
| `HOLD_BAND_KMH` | 0.1 | 凍結帯 |
| `FAST_ENGAGE_KMH` / `FAST_RELEASE_KMH` | 0.5 / 0.3 | 速い層のヒステリシス |
| `TRIM_RATE_PCT_S` | 3.0 %/s | 低速トリムのスルーレート |
| `TRIM_STEP_PCT` | 0.25 % | 低速トリムの量子化 |
| `TRIM_SLOW_KP_RATIO` | 1.0 | 低速層 KP = 速い層実効 kp（層の権限逆転を構造的に禁止） |
| `ZERO_CROSS_BLEED_FACTOR` | 0.15 | 偏差符号反転時に積分・出力を 0.15 倍へブリード |
| `SIMC_TAU_C_FACTOR` | 1.5 | τc = 1.5θ |
| `pid_output_limit_pct` | 50 % | 速い層 PID の出力上限 |

### 3-4. 実効ゲインの決まり方（二重ゲインスケジュールの min）

```
  gain_scale = min(  clamp( g(v) / g_nominal , 0.5, 1.5 ) ,   Kc(v, side) / kp  )
                     └────── ① FF モデルの局所勾配 ──────┘   └── ② SIMC 上限 ──┘

  ① g(v)      : FF 逆モデルへ a=±0.5km/h/s を与えた差分 ∂開度/∂a（GainSchedule）
     g_nominal: 1 / k'_accel(60km/h) = 3.61
  ② Kc(v,side) = 1 / ( k'(v,side) · (θ + 1.5θ) )       （models/profile.py robust_kp_at）

  実効比例ゲイン kp_eff = kp × gain_scale = min( kp·①, Kc )
```

`000_sample`（kp=1.837、θ=1.05s、τc=1.575s）での **Kc(v)** と、
そこから決まる実効ゲインの上限:

| v [km/h] | k'_accel | k'_brake | **Kc 駆動側** | **Kc 制動側** | 制動側で 5% を出すのに要る偏差 |
|---|---|---|---|---|---|
| 15 | 0.517 | 0.147 | 0.74 | 2.58 | 1.9 km/h |
| 25 | 0.478 | 0.254 | 0.80 | 1.50 | 3.3 km/h |
| 45 | 0.334 | 0.477 | 1.14 | 0.80 | **6.3 km/h** |
| 60 | 0.277 | 0.738 | 1.37 | 0.52 | **9.7 km/h** |
| 75 | 0.226 | 1.067 | 1.68 | 0.36 | **14.0 km/h** |
| 100 | 0.218 | 1.317 | 1.75 | 0.29 | **17.3 km/h** |
| 120 | 0.267 | 1.399 | 1.43 | 0.27 | **18.4 km/h** |

（`kp·①` は [0.92, 2.76] の範囲に入るため、上表の Kc が 0.92 を下回る欄では
**必ず Kc が binding**＝実効ゲインは PID 適合値ではなく SIMC 上限そのものになる）

### 3-5. フェーズ権限（`_apply_phase_authority`）

速い補正層が**非アクティブ**のときだけ、フェーズが許す向きへ合成 effort を制限する。

| phase | 速い層 非アクティブ時 | 削った向き | 速い層 アクティブ時 |
|---|---|---|---|
| `DRIVE` | effort<0 を 0 に | 制動側飽和 | **無制限**（plan+trim をそのまま） |
| `BRAKE` | effort>0 を 0 に | 加速側飽和 | 同上 |
| `COAST` | effort を 0 に | 両側飽和 | 同上 |
| `STOP_HOLD` | `base_effort` のみ（トリム無効） | 両側飽和 | **STOP_HOLD だけは常にプラン支配** |

削った向きは飽和フラグとして次サイクルのトリム積分を止める（ワインドアップ防止）。

### 3-6. 最小実効ブレーキ昇格（`_apply_min_effective_brake`）

ブレーキ不感帯 5.0% により (−5, 0) の effort は調停器で開度 0 に丸められる。
「制動を指令したのに物理的に効かない」状態を避けるため、次の**すべて**を満たすとき
effort を **−5.0% ちょうど**へ引き上げる。

```
  条件: db>0 かつ phase≠STOP_HOLD
        かつ trim.is_fast_active           （|偏差| が 0.5 を超えて介入中）
        かつ actual − ref_pid > 0          （超過速度＝制動が正しい向き）
        かつ −5.0 < effort < 0             （調停器が 0 に丸める帯）
  →     effort = −5.0
  解除: 速い補正層の離脱（|偏差| < 0.3）まで保持
```

> 注: `引き継ぎ20260909.md` では `_escalate_brake_deadband` という名前で参照されているが、
> 実装上の関数名は `_apply_min_effective_brake`（`drive_loop.py:694`）である。

### 3-7. ペダル調停（`PedalArbiter.arbitrate`）

符号付き effort → (accel_opening, brake_opening) の唯一の写像点。

```
 effort ─┬─ |effort| ≤ h=0.5 ──────────────→ coast（アクセルを 10%/s で漸減、ブレーキ 0）
         ├─ effort > +0.5 ─→ ブレーキ直後 0.3s 以内？ ─yes→ coast（加速側飽和）
         │                        │no
         │                        ▼
         │                   不感帯逆補償(accel_db=0.5) → レート制限 200%/s
         │                   → max_accel でクランプ → 変化 <0.2% なら前回値保持
         │                        └→ (accel, 0)
         └─ effort < −0.5 ─→ 不感帯逆補償(brake_db=5.0) → レート制限 300%/s
                              → max_brake でクランプ  └→ (0, brake)  ※アクセルは即 0

  不感帯逆補償: |m| < db/2 → 0 ;  それ以外 → max(db, |m|)
```

| 定数 | 値 |
|---|---|
| `switch_hysteresis_pct` | 0.5 % |
| `accel_reengage_dwell_s` | 0.3 s（制動側にディレイなし） |
| `accel_rate_limit_pct_s` / `brake_rate_limit_pct_s` | 200 / 300 %/s |
| `accel_release_rate_pct_s` | 10 %/s |
| `accel_min_step_pct` | 0.2 % |
| `accel_deadband_pct` / `brake_deadband_pct` | **0.5 / 5.0 %** |

最終段で `enforce_pedal_exclusion` が同時踏みを再度禁止し（保険）、
`opening_to_position` でパルス位置へ換算して両軸へ書き込む。

## 4. 層3: 走行後エピソード学習（ILC）

自動走行が**正常完了したときだけ**起動する（手動停止・非常停止は学習しない）。
`robot_controller._finish_auto_drive_with_plan_update` → `PedalPlanService.update_from_session`。

### 4-1. プラン更新則（`update_plan`）

```
  次回プラン = snap( clamp_by_phase(
                  base + clip( Q( u_applied(t) + L(v)·e(t+Δ) ) − base , ±8.0% ) ) )

    base      : 現行 FF モデルで**毎回作り直した**基準プラン（層2 の出力）
    u_applied : 前走行の applied effort（権限クランプ後・調停器前）を 0.1s グリッドへ補間
    e(t+Δ)    : 前走行の偏差を **Δ = θ + 0.5 = 1.55 s 先**から引く
    L(v)      : factor / (k'(v) · Δ) 、factor = 0.25
    Q         : ゼロ位相ローパス 0.2 Hz（RC 0.80s、forward-backward）★非因果
    clip      : base との差分を ±8.0 % に制限
```

| 定数 | 値 | 効果 |
|---|---|---|
| `PLAN_LEAD_RESPONSE_S` | 0.5 s | Δ = θ + 0.5（θ 依存） |
| `PLAN_L_GAIN_FACTOR` | 0.25 | 学習ゲイン |
| `PLAN_UPDATE_CUTOFF_HZ` | **0.2 Hz** | **候補プランを前後 ±0.8s ににじませる** |
| `PLAN_DELTA_LIMIT_PCT` | **8.0 %** | 基準プランからの乖離上限 |
| `MIN_LOGS_FOR_UPDATE` / `MIN_COVERAGE_RATIO` | 50 件 / 0.9 | ガード |

**フェーズ列は base のまま固定**され、effort だけが更新される。

### 4-2. 採否 3 値（`PedalPlanService._decide_outcome`）

```
   reward > best                    → ACCEPT   最良を更新し、実測から次回候補を生成
   best − 2σ < reward ≤ best        → EXPLORE  最良据え置き、候補は生成（探索継続）
   reward ≤ best − 2σ               → ROLLBACK 最良プランへ復帰して凍結
   σ が推定できない（履歴 3 本未満） → EXPLORE
```

σ は同一報酬スケールの直近 5 件の標本標準偏差。

### 4-3. 報酬関数（`reward.reward_score`）

```
  reward = −( 1.0·track + 0.4·smooth + 0.2·switch + 0.2·phase )

    track  = p95/0.4  +  2.0·max/1.0  +  10.0·over_limit_integral[km/h·s]
    smooth = effort 変化率 RMS / 2.0
    switch = ペダル交互踏み 回/min
    phase  = フェーズ逸脱積分 / 走行時間 [%]
```

第3ラウンド通算ベスト（iter 10）での内訳:

| 項 | 値 | 寄与 | 占有 |
|---|---|---|---|
| p95 / 0.4 | 1.42 / 0.4 | 3.55 | 2.4 % |
| 2 × max / 1.0 | 2 × 4.057 | 8.11 | 5.5 % |
| 10 × 超過積分 | 10 × 9.431 | **94.31** | **89.0 %** |

### 5-1. θ（むだ時間）の同定方法

`pid_tuning._segment_fopdt`。**車速追従の位相を決める最重要パラメータ**にもかかわらず、
測り方は次のとおり素朴である。

```
  区間抽出: accel_opening ≥ 5.0 % かつ brake_opening ≤ brake_db が続く連続区間
  θ = (区間開始から実車速が +0.3 km/h 上昇するまでのサンプル数) × dt
      dt = ログの中央値サンプル周期 = 0.1 s（50ms ループを 2 サイクル間引き）
      上限 3.0 s でクランプ、区間ごとの中央値を採用
```

| 制約 | 影響 |
|---|---|
| 分解能 0.1 s | θ が 0.1s 刻みでしか出ない |
| 区間開始 = 開度が 5% を跨いだ瞬間 | ペダル自体の移動時間・踏み込みランプが θ に混入 |
| しきい値 0.3 km/h | CAN 車速の隣接差 std ≈ 0.22-0.25 km/h と同オーダー。ノイズ 1 サンプルで θ=0 になりうる |
| 中央値集約（最小 2 区間） | 区間数が少ないと 1 区間の外れ値が支配 |

実績（5 サイクル）: **0.30 / 0.70 / 0.50 / 0.80 / 1.05 s** ＝ 3.5 倍のばらつき。

## 7. KPI はどこで・どう測られているか

`KPIMonitor`（`kpi_monitor.py`）が**制御サイクル内で全サンプル**を集計する
（ログは 2 サイクル間引きのため、オフライン解析では違反を観測しきれない）。

| KPI | 定義 | 実装 |
|---|---|---|
| p95 | \|actual − ref\| の 95 パーセンタイル（0.01km/h ビンの上端値＝保守側） | `p95_kmh()` |
| max | \|actual − ref\| の最大値 | `_max_abs_deviation` |
| 符号反転 | 偏差が **±0.3 km/h を両側で超えた**往復を、任意 5 秒窓での最大回数で数える | `SIGN_REVERSAL_AMPLITUDE_KMH` |
| 超過積分 | ∫ max(0, \|dev\| − 1.0) dt（dt は 0.5s でクランプ） | `over_limit_integral_kmhs` |

**重要**: 集計に使う `ref` / `actual` は **now-frame の生値**である
（`plan_lead_s` も フィードバック LPF も通していない）。一時停止中は集計しない。

## 8. KPI 未達の構造的要因（制御フローから読み取れること）

以上のフローから、KPI 未達の原因は**ゲイン調整で動く領域には無い**。
6 つの構造的要因に分解できる（①〜⑤は制御フローの内側、⑥は外側）。

### 要因 × KPI の対応

| # | 要因 | p95 | 最大逸脱 | 符号反転 | 主な根拠コード |
|---|---|---|---|---|---|
| ① | 前倒し・非因果平滑が**向きを区別せず**重畳（合計 ≈2.5s） | ○ | **◎** | ○ | P1〜P5（6-1 表） |
| ② | フィードバック権限が SIMC 上限で構造的に小さい（特に制動側） | ◎ | **◎** | — | A5, A6 |
| ③ | ブレーキ不感帯 5% の二値化 | ◎ | **◎** | **◎** | A1, A2, A8, A9 |
| ④ | θ の同定が不安定で ①②⑤ を同時に振り回す | ○ | ○ | ○ | 5-1 節 |
| ⑤ | 学習則が最大逸脱に到達できない | — | **◎** | — | A3, P4, P5, 4-2, 4-3 |
| ⑥ | 120km/h 帯の 0.57Hz 変動（計測床の疑い） | ○ | ○ | ◎ | `can_reader.py` |

（◎ = 主要因、○ = 寄与、— = ほぼ無関係）

---

### ① 前倒し・非因果平滑が「向き」を区別しない

**構造**: 6-1 表のとおり、**進み 1.97 s ＋ にじみ ±1.3 s**が加算される。
これらはすべて **effort を増やす方向にも減らす方向にも同じだけ**掛かる。

- むだ時間補償として前倒しが正当化されるのは**ランプ区間**（要求が単調に変化する区間）である。
- **折返し点**（加速→減速の頂点、減速率が緩む点）では、前倒しは
  「基準がまだ加速を要求しているのにアクセルを抜く」という**真逆の操作**になる。

```
   基準速度       ／‾‾‾＼            ← 頂点 t=145.9
   要求 a_req    ／     ＼
                ─────────
   プラン effort ／‾‾＼               ← 2.5 秒早く抜き始める
                       ＼____
   実車速        ／‾‾‾‾            ← 43.5 km/h で頭打ち
   偏差                  ＼____      ← −5.14 km/h（max の記録）
                 143   145   147 [s]
```

**コード上の裏付け**: `plan_t = elapsed_s + self._plan_lead_s` も
`e_shifted = np.interp(grid + delta_s, ...)` も、**符号・向きの分岐を一切持たない**。
`required_accel` のセンタリング窓も `zero_phase_lowpass` も同様に対称である。

**この要因が最大逸脱を作っている理由**: 折返し点は基準軌跡の中で
「要求 effort の時間微分が最大」の点であり、時間軸の誤差 Δt がそのまま
`|Δeffort| = |d(effort)/dt| × Δt` の指令誤差になる。
45 km/h 付近では要求開度が 17% → 0% へ 1 秒で動くため、Δt=2.5s は指令を丸ごと失わせる。

### ② フィードバック権限が構造的に小さい（特に制動側）

**構造**: 実効比例ゲインは `min(kp·①, Kc(v, side))` で決まり、
3-4 の表のとおり **Kc が binding するケースがほとんど**である。
その結果:

| 状況 | 実効 kp | 5 km/h の偏差に対する補正 |
|---|---|---|
| 45 km/h・駆動側 | 1.14 | 5.7 % |
| 75 km/h・駆動側 | 1.68 | 8.4 % |
| 45 km/h・**制動側** | 0.80 | 4.0 % |
| 75 km/h・**制動側** | 0.36 | **1.8 %** |
| 120 km/h・**制動側** | 0.27 | **1.4 %** |

**帰結 1（最大逸脱を戻せない）**: 頂点エピソードで観測された
「トリムが +4.06% で頭打ち」は出力上限（50%）でも飽和でもなく、
**`Kc × 偏差` そのもの**である。プランの不足分（約 5%）を埋めるには
偏差がさらに 4〜5 km/h 必要になる。**速い補正層は「max ≤ 1.0 の安全網」として
設計されているが、その権限は max ≤ 1.0 を守れる大きさになっていない。**

**帰結 2（制動側で実質オフになる）**: `_is_accel_side` は
**基準速度のトレンド**で駆動側／制動側を選ぶ（`drive_loop.py:726-734`）。

```
   is_accel_side = ( ref(t + 0.5s) − ref(t) ) ≥ −0.1 km/h
```

つまり**減速区間では常に制動側の Kc が選ばれる**。ところが減速区間で必要な補正は
「減速しすぎたのでアクセルを当てる」＝**駆動方向**であることが多い。
制動側 Kc は高速域で 0.27〜0.36 と極小なので、この局面で FB はほぼ効かない。
**brake フェーズの p95 が 2.30（drive は 1.24）と倍悪いことの、コード上の説明になる。**

**帰結 3（PID 適合の結果が使われていない）**: 3-4 の表のとおり
`Kc < kp × 0.5` となる速度域が広く、`REFINE_1` の座標降下が選んだ kp は
そこでは一切効かない。層4 の PID 適合フェーズは、実効ゲインに対してほぼ無力である。

### ③ ブレーキ不感帯 5% の二値化

**構造**: ブレーキ側は **4 か所**で同じ量子化を受ける。

```
   プラン生成    snap_efforts_to_deadband  : |e|<2.5 → 0 、それ以外 → −max(5.0,|e|)
   ILC 候補      snap_efforts_to_deadband  : 同上
   実行中        _apply_min_effective_brake: (−5,0) → −5.0（速い層アクティブ＆超過時）
   調停          _apply_deadband           : 同上
```

**制動 effort は物理的に {0} ∪ [5%, ∞) しか取れない。** その 1 段目の効き:

| v [km/h] | 5% ブレーキの追加減速度 | KPI 許容 (p95 0.4 km/h) との比 |
|---|---|---|
| 45 | 2.38 km/h/s | 1 サイクル(50ms)で 0.12 km/h |
| 75 | **5.33 km/h/s** | 1 サイクルで 0.27 km/h |
| 120 | **7.00 km/h/s** | 1 サイクルで 0.35 km/h |

**帰結 1**: 微調整のための制動が存在しない。1 段踏むだけで p95 の許容幅を
1〜2 サイクルで使い切る。

**帰結 2（低速トリム層は制動を追加できない）**: 低速トリム層は
レート 3 %/s・量子化 0.25 % なので、合成 effort を 0 から −5% へ動かすのに **1.7 秒**かかり、
その間の開度は 0（不感帯内）のままである。`_apply_min_effective_brake` は
速い補正層アクティブ時にしか働かない。つまり
**偏差 0.1〜0.5 km/h の帯（＝ p95 0.4 を守るために最も精度が要る帯）では、
フィードバックが制動を追加する経路が構造的に存在しない。**
この帯で制動を出せるのはプラン（層2/層3 が事前に置いた値）だけである。

**帰結 3（過制動 → 反対側への振れ）**: `_apply_min_effective_brake` の解除条件は
「速い補正層の離脱」＝**偏差が 0.3 km/h を切るまで**である。5% の一段が
75 km/h で −5.33 km/h/s ある以上、0.3 km/h まで詰める頃には行き過ぎており、
反対側（不足側）へ振れる。これが**符号反転 KPI（7〜8 回/5s）を単独で落としている**。

### ④ θ の同定が不安定で、3 経路を同時に振り回す

θ は 5-1 のとおり素朴な推定量で 0.30〜1.05 s（3.5 倍）にばらつく。
そして θ は**互いに独立でない 3 か所**へ同時に効く。

| 波及先 | 式 | θ=0.50 | θ=1.05 | 比 |
|---|---|---|---|---|
| FB ロバスト上限 Kc（60km/h 駆動側） | `1/(k'·2.5θ)` | 2.89 | 1.37 | 2.1× |
| プラン参照の前倒し | `min(0.4θ, 0.5)` | 0.20 s | 0.42 s | 2.1× |
| ILC リード Δ | `θ + 0.5` | 1.00 s | 1.55 s | 1.55× |
| SIMC 初期ゲイン kp/ki | `1/(k'·2.5θ)`, `Ti=4·2.5θ` | — | — | 2.1× |

**帰結**: サイクルごとに**制御器そのものが別物になる**。ILC は
「毎回違うプラントに対して、毎回違うリード時間で学習している」状態であり、
反復間の比較可能性が保証されていない。要因①（前倒し）と要因②（FB 権限）の
**両方を同時に動かす**ため、実機結果からどちらの効果か切り分けることもできない。

### ⑤ 学習則（ILC）が最大逸脱に到達できない

報酬の 89% が超過積分（＝ max 違反の量）であり、ILC は max を最も強く狙っている。
にもかかわらず 13 反復で max は 3.82〜5.19 の範囲で横ばいだった。
制御フロー上の理由は 4 つある。

| # | 障害 | 実装 | 内容 |
|---|---|---|---|
| ⑤-a | **操作対象がタイミングを含まない** | `plan_update.update_plan` | ILC が動かせるのは effort の**値**だけ。P1〜P5 の時間軸パラメータは学習対象外 |
| ⑤-b | **Δlimit ±8% が頂点で binding** | `plan_update.py:205` | 頂点で必要な開度 16.9% に対し基準プランは 6〜12%。差 5〜11% は上限に張り付く |
| ⑤-c | **候補プランが 0.2Hz でにじむ** | `plan_update.py:202` | RC 0.80s のゼロ位相 LPF。**折返し点に鋭いピークを立てられない**（作っても前後へ拡散する） |
| ⑤-d | **不感帯スナップで解が消える** | `plan_update.py:207` | 制動側の細かい補正は 0 か 5% に丸められ、学習の勾配が失われる |
| ⑤-e | **採否基準が層4 と不整合** | `plan_service._decide_outcome` | ILC 採否は reward 単独。学習サイクルの最良選択は (KPI合否, −p95, reward) の辞書順。iter 12（p95 1.43＝サイクル最良）は max 5.14 のため不採用になり、iter 13 でロールバックされた |

**⑤-b は特に重要**である。ILC が「タイミングではなく値の誤り」だと仮定しても、
そもそも**必要な値に届く前にクランプされる**。
`base_plan` は毎回 FF モデルから作り直され（＝要因① の非因果平滑を必ず含む）、
学習はその ±8% の帯の中でしか動けない。

### ⑥ 120 km/h 帯の 0.57Hz 変動（計測床の疑い）

`CANReader.read_speed` はキャッシュされた最新値をそのまま返し、
補間・外挿・フィルタを一切行わない（`can_reader.py:158-196`）。
制御側にも評価側にも生値が流れる（フィードバックだけ τ=0.25s の LPF が入る）。

120 km/h プラトーでの偏差 std は FB 権限を上げても 0.72 → 0.57〜0.62 にしか下がらず、
**第2ラウンドから同じ大きさで存在する**。制御が作ったものではない可能性が高い。
p95 の閾値 0.4 km/h は 2026-07-16 に「生 10Hz 車速の変動が p95≈0.4 ある」ことを根拠に
0.2 から緩めた経緯があり（`kpi_monitor.py:23-27`）、**120km/h 域では実測の床が
さらに高い可能性がある**。これは制御フローの外側の問題で、切り分けが要る。

## 9. 制御フローから導かれる打ち手の位置づけ

原因が制御フローのどの段にあるかで、手を入れるべき場所は一意に決まる。

| 要因 | 手を入れる段 | 実装位置 | ILC で解けるか |
|---|---|---|---|
| ① 前倒しの向き無区別 | P3, P4（+ P1, P5） | `drive_loop.py:433`, `plan_update.py:184`, `pedal_plan.py:143` | **解けない**（学習対象外） |
| ② FB 権限 | A5, A6 と `_is_accel_side` | `profile.py:132`, `drive_loop.py:413-425, 726` | 解けない（プラン側の量ではない） |
| ③ 不感帯二値化 | A1/A2/A8/A9 | `pedal_plan.py:311`, `drive_loop.py:694`, `pedal_arbiter.py:144` | **解けない**（表現できる解が無い） |
| ④ θ の不安定 | 5-1 の同定式 | `pid_tuning.py:124-130` | 解けない（学習の前提条件） |
| ⑤ 学習則の到達限界 | A3, P5, 採否 | `plan_update.py:202-207`, `plan_service.py:109-128` | 学習則自身の修正 |
| ⑥ 計測床 | 制御フローの外 | `can_reader.py` / KPI 定義 | 解けない |

**①②③ はいずれも「ILC の操作対象の外」にある。**
`引き継ぎ20260909.md` の「max を下げるには ILC の外側を変えるしかない」という結論は、
制御フローの構造からも同じ結論になる。
