## 0. 一言でいうと

第3ラウンドの修正は**狙った 4 つの機構がすべて意図どおり動いた**（ILC が初めて反復で改善し、
停止保持違反は消え、フィードバックの実効ゲイン逆転も解消した）。
しかし**プライマリー KPI は 3 つとも未達**で、しかも 2 つの追従 KPI で様子がまったく違う:

| プライマリー KPI（PRD） | 上限 | 第2ラウンド | 第3ラウンド | 13 反復での動き |
|---|---|---|---|---|
| 車速追従精度（通常）: \|偏差\| p95 | ≤ 0.4 km/h | 1.93 | **1.42** | 2.92 → 1.42（**−51%**） |
| **車速追従精度（最大逸脱）: \|偏差\| max（例外なし）** | **≤ 1.0 km/h** | 4.70 | **4.06** | **3.82〜5.19 で横ばい（改善ゼロ）** |
| 振動抑制: 符号反転 | ≤ 1 回 / 5s | 6 | 7〜8 | 悪化（FB 権限を上げた副作用） |

**p95 は半分になったが、最大逸脱はまったく改善していない。**
ILC を 13 反復回しても max は 3.82〜5.19 km/h の間を上下しただけで、
PRD が求める「全走行区間で 1.0km/h を超えない（例外なし）」に対し、
**1 走行あたり 12〜14 回・走行時間の 8.8〜12.4% が違反**という状態が続いている。
最大逸脱は p95 と同格の Must KPI なので、**次ラウンドはここを主目的に置く必要がある**（詳細は 3-3）。

残った誤差は制御ゲインの問題ではなく、**4 つの構造的な要因**に移った:

1. **プランがコーナー／軌跡頂点で約 2.5 秒早くペダルを抜く**（**最大逸脱の最大要因**。第2ラウンドから未解決、むしろ悪化）→ 4-③ / 対策は優先 A
2. **ブレーキ不感帯 5% による「0 か 5%」の構造的量子化**（**最大逸脱の第2要因**。車両側の物理制約・回避策の設計が要る）→ 4-④ / 対策は優先 B
3. **むだ時間 θ の同定値がサイクルごとに 0.30〜1.05s とばらつき、FB 権限が毎回 2〜3.5 倍変わる**（新規発見。max を守る安全網＝速い補正層の権限が毎回変わる）→ 4-② / 対策は優先 C
4. **報酬の 89% が「ハード違反積分」＝ max を最重視しているのに max が改善しない ＝ ILC の操作対象（プラン値）では届かない領域に max がある**（新規発見）→ 4-① / 対策は優先 D

さらに **120km/h プラトーに 0.57Hz・偏差 std 0.57〜0.72km/h の変動**があり（4-⑤）、
これは第2ラウンドから同じ大きさで存在する＝制御起因ではない。
**最大逸脱 1.0 を切れるかどうかは、最終的にこの変動の出所（計測かダイナモか）に依存する**（優先 E）。

#### なぜ ILC では max が下がらないのか

報酬の 89% は超過積分（＝max 違反の量）で占められている（4-①）。
**つまり ILC は max を最も強く狙っているのに、13 反復して下げられていない。**
これは重み付けの問題ではなく、**ILC の操作対象では届かない**ことを意味する:

- ILC が動かせるのは**プランの effort 値**だけで、**プランの時間軸（前倒し量・平滑窓）は動かせない**。
  A（頂点早抜け）は effort の大きさではなく**タイミング**の誤りなので、
  プラン値をどう調整しても「2.5 秒早く抜く」形は消えない。実際 3 本すべて同じ波形で −4.0〜−5.1 が出ている。
- B はアービタ／不感帯の**量子化**が原因で、プラン側にそもそも表現できる解がない
  （0% と 5% の間の effort は物理的に出せない）。
- したがって **max を下げるには、ILC の外側（プラン生成のタイミング設計と、ブレーキ不感帯の扱い）を
  変えるしかない。** ゲイン調整でも反復回数を増やしても到達しない。

#### 目標との距離（正直な見積り）

- A を潰せば max は 4.06 → **約 2.5**（次に大きい B のピーク 2.39-2.48 が新しい max になる）
- A と B の両方を潰して初めて max は **1.5〜1.7 前後**（C の 1.68/1.74 が残る）
- そこから 1.0 を切るには **優先 E（120km/h 帯の 0.57Hz 変動が計測由来か制御由来か）の決着が必要**。
  この変動は単独で偏差 std 0.57〜0.72km/h あり、ピークは 1.2〜1.7km/h に達する。
  **計測由来だと判明した場合、「例外なし」の達成可否そのものをユーザーと再確認する必要がある。**

## 4. 根本原因（第3ラウンドの実測で新たに確定したもの）

### ① 報酬の 89% は「ハード違反積分」＝ max を最重視しているのに、max が下がらない

`src/domain/control/reward.py:64-74`

```python
track = p95/0.4  +  2.0*max/1.0  +  10.0*over_limit_integral_kmhs
```

実測での内訳（iter 10 = 通算ベスト）:

| 項 | 値 | reward への寄与 | 占有率 |
|---|---|---|---|
| p95 / 0.4 | 1.42 / 0.4 | 3.55 | **2.4%** |
| 2 × max | 2 × 4.057 | 8.11 | 5.5% |
| 10 × 超過積分 | 10 × 9.431 | **94.31** | **89.0%** |
| 合計 track | | 105.97 | |

iter 12 でも同じ（超過積分項 131.6 / 合計 147.4 = 89%）。

**帰結は 2 つある。**

**(a) 重み付け自体は PRD と整合している。** ILC は「1.0 km/h を超えた量×時間」＝
最大逸脱 KPI をほぼ純粋に最小化しており、これは「最大逸脱は例外なし」という
PRD の優先度と合っている。**したがってこの重みを下げてはいけない。**

**(b) それでも max は 13 反復で下がらなかった**（3-3）。報酬が最も強く押している対象が
動かないということは、**ILC の操作対象（プランの effort 値）では届かない場所に max がある**
ということ。実際 max を作っている A（頂点早抜け）は effort の大きさではなく
**プランのタイミング**の誤りで、ILC は時間軸を動かせない。
**max を下げるには ILC の外側（プラン生成のタイミング設計・ブレーキ不感帯の扱い）を変えるしかない。**

**副作用として p95 側は勾配を失っている。** p95 は係数上 2.4% しか効かず、
iter 12 は p95 1.43（サイクル最良）を出したが max 5.14 の一撃で reward が伸びず「explore＝不採用」
となり、iter 13 でロールバックされた。**p95 を改善したプランが p95 以外の理由で捨てられている。**
ただしこれは超過積分を弱めて直すのではなく、**p95 項の係数を上げる／採否を辞書順にする**で直す（優先 D）。

> 補足: 学習サイクルの best 選択（`learning_cycle.py`）は第2ラウンドで
> 「KPI 合否 → p95 → reward」の辞書順に直したが、**ILC の採否（`plan_service._decide_outcome`）は
> reward 単独のまま**で、ここが直っていない。

### ② むだ時間 θ の同定値がサイクルごとに 3.5 倍ばらつく

第3ラウンドで FB ゲインを積分系 SIMC `Kc = 1/(k'(v)·(θ+τc))`, `τc = 1.5θ` に張り替えた
（`src/models/profile.py:132`）。**Kc は θ に反比例する。** その θ の同定実績:

| サイクル | θ [s] | stage1 kp | 45km/h 駆動側の Kc |
|---|---|---|---|
| `0a0b06a0` (9/07) | 0.30 | 1.490 | 3.99 |
| `3ca20d43` (9/08) | 0.70 | 1.010 | 1.71 |
| `9eee549b` (9/09 午前) | 0.50 | 0.846 | 2.39 |
| `d9f5558d` (9/09 13:50) | 0.80 | 2.591 | 1.50 |
| `979fb2f5` (9/09 15:41) | **1.05** | 1.837 | **1.14** |

θ は `identify_fopdt` の「区間開始 → 車速が 0.3km/h 上昇するまで」で測っている
（`src/domain/pid_tuning.py:117-122`）。プラトー前提ではないので第2ラウンドで「有効」と判断した
指標だが、**実際には 0.30〜1.05s（3.5 倍）で暴れており、そのまま FB 権限を決めている。**

さらに θ は 3 か所へ同時に波及する:

| 波及先 | 定義 | θ=0.5 のとき | θ=1.05 のとき |
|---|---|---|---|
| FB ロバスト上限 | `Kc = 1/(k'·2.5θ)` | 2.39 | **1.14** |
| プラン前倒し | `min(0.4θ, 0.5)` | 0.20s | **0.42s** |
| ILC リード Δ | `θ + 0.5` | 1.00s | **1.55s** |

第3ラウンドの計画は θ=0.5 前提で「実効 kp 2.4〜3.2」を狙っていたが、
**実機で θ=0.8〜1.05 が出たため、FB 権限は狙いの半分以下（1.14〜1.50）にしかなっていない。**
これが「ゲインを上げたのに trim 寄与率が 6.3% しかない」ことの直接の理由。

### ③ プランがコーナー／頂点で約 2.5 秒早くペダルを抜く（未解決・むしろ悪化）

`5ac4f31d` t=143〜146 の実測（基準は t=145.85 まで **+2.0 km/h/s で上昇し続けている**）:

```
  t     ref    act    err   dref    plan   trim    appl   phase
143.4  43.05  42.46  -0.59  +2.01   15.26  +0.51   15.77  drive   ← ここからプランが抜き始める

144.6  45.45  43.46  -1.99  +2.00   11.58  +1.78   13.36  drive   ← 実車速が 43.5 で頭打ち

145.5  47.25  43.20  -4.05  +2.00    6.19  +4.06   10.25  drive   ← トリム飽和
```

- トリムは **+4.06% で頭打ち**になり、不足分（約 5%）を埋めきれない。

| 要素 | 定義場所 | θ=1.05 での量 |

「早すぎるアクセル解放」として真逆に働いている。**
前倒しは *ランプ区間* には効くが *折返し点* では害になる、という向きの区別が入っていない。

### ④ ブレーキ不感帯 5% による「0 か 5%」の構造的量子化

同定されたブレーキ不感帯は **5.0%**（プロファイル `3937e81b` / `000_sample`）。
アービタ（`pedal_arbiter.py:145-159`）は `|effort| < 2.5 → 0`, `≥2.5 → max(5.0, |effort|)` に丸める。

学習運転（`d6790ef4`）でブレーキ 1〜4% を実際に踏んだときの減速度は惰行とほぼ同じで、
**5% を超えて初めて効き始める**ことが実測で確認できる ＝ 不感帯 5% は実在する物理量。

| ブレーキ開度 | n | 平均減速度 | 中央値車速 |
|---|---|---|---|
| 1-2% | 205 | −1.37 | 99 km/h |
| 2-3% | 201 | −1.52 | 93 km/h |
| 3-4% | 192 | −1.75 | 89 km/h |
| **5-6%** | 189 | **−3.31** | 80 km/h |

不感帯 5% の 1 段目が生む追加減速度は **45km/h で 2.4 km/h/s、75km/h で 5.3 km/h/s**。
KPI の許容 0.4 km/h に対して桁が違う。

さらに `drive_loop._escalate_brake_deadband`（`drive_loop.py:700-724`）が、
速い層アクティブ＋超過速度＋effort が (−5, 0) のとき **effort を −5.0% へ引き上げる**。
これは「0 か 5% の中で偏差最小を狙う唯一の手段」として意図的に入れたものだが、実測では
過制動の連鎖を作っている:

```
  t     ref    act    err   dref    plan   trim    appl   brk%
81.7  72.88  75.01  +2.13  -5.01   -4.42  -0.65   -5.07   5.07  ← 微小な超過
82.0  71.75  74.16  +2.40  -1.99    0.00  -0.78   -5.00   5.00  ← plan+trim=-0.78 → -5.0 へ昇格
83.8  68.15  69.28  +1.13  -2.00    0.10  -0.62   -5.00   5.00
84.1  67.55  68.39  +0.84  -2.00    1.18  -0.53    0.65   0.00  ← 解除
88.0  59.75  58.40  -1.35  -2.00    7.26  +0.66    7.92   0.00  ← 反対側へ 1.35 km/h 行き過ぎ
```

**+2.4 の超過を消すために 5% ブレーキを 2 秒入れ、−1.35 の不足へ振れる。**
これが brake フェーズ p95 2.30 と符号反転の主因。

### ⑤ 120 km/h プラトーに 0.57 Hz の変動があり、これ自体が p95 の床になっている

`ref > 119.5` の区間（105 サンプル）の実測:

| `a7dc98f6`（第2ラウンド） | 0.846 | 0.720 | 1.33 | 6 | 0.61 |

## 6. 今後の手段（優先順）

### どの手段がどの KPI を担当するか

**最大逸脱（≤1.0・例外なし）は p95 と同格の Must で、しかも 13 反復まったく改善していない。**
次ラウンドの主目的はここに置く。

| 手段 | 主に効く KPI | 見込み |
|---|---|---|
| **優先 A: 頂点/コーナーの早抜けを止める** | **最大逸脱** | max 4.06 → 約 2.5 |
| **優先 B: ブレーキ不感帯 5% の扱いを設計しなおす** | **最大逸脱**・符号反転 | max → 1.5〜1.7 |
| 優先 C: θ の安定化 | p95・最大逸脱（安全網の権限を毎回同じにする） | 走行間ばらつきの縮小 |
| 優先 D: ILC 採否を辞書順に揃える | p95 | 反復が止まらなくなる |
| 優先 E: 120km/h 帯 0.57Hz 変動の切り分け | **最大逸脱**・p95・符号反転 | 1.0 を切れるかの可否判断 |
| 優先 F: 積み残し | — | — |

**A → B を潰さない限り max は動かない**（3-3 の内訳より、max の記録は常に A、違反時間の
最大シェアは B）。C・D は p95 と学習の安定性が主で、max への直接効果は小さい。

### 優先 A — プランの前倒しを「向き別」にして折返し点での早抜けを止める【最大逸脱の第1要因】

**問題**: 前倒し（ILC リード 1.55s ＋ プラン 0.42s ＋ 非因果平滑 0.5s ≒ 2.5s）が
折返し点でアクセルを早く抜き、**13 反復すべてで max の記録を作っている**（−4.0〜−5.1km/h）。
ILC はこれを直せない（3-3 参照。effort 値ではなくタイミングの誤りのため）。

**案**（いずれか、または併用）:
1. **前倒し量を要求 effort の変化方向で切り替える**。effort を**増やす**方向（踏み増し）には
   むだ時間ぶん前倒しし、**減らす**方向（抜き・解放）には前倒しを 0 にする。
   むだ時間補償は「遅れて効く操作を早く出す」ためのもので、解放側は遅れても
   惰行・エンジンブレーキが働くので害が小さい。
2. センタリング窓 `PLAN_ACCEL_SMOOTH_S = 1.0`（`pedal_plan.py:43`）を**因果的な後方窓**に変える。
   第3ラウンドで「幅を 0.3 に狭めると閉ループ模擬で悪化する」ことは確認済みなので、
   幅ではなく**窓の中心位置**を動かすのが正しい方向。
3. 折返し点（`required_accel` の符号反転点）だけ平滑と前倒しをバイパスする。

**判定**: `5ac4f31d` の t=144-148 相当のエピソードでピーク偏差が −5.1 → −2 以下になること。
**max がここで 4.06 → 2.5 前後まで落ちれば成功。** 実機前に
`scripts/simulate_control.py`（閉ループ模擬）で順位付けできる。

### 優先 B — ブレーキ不感帯 5% への対処を設計しなおす【最大逸脱の第2要因】

**問題**: 0〜5% の中間制動力が構造的に出せない。現在の `_escalate_brake_deadband` は
「0 か 5% のデューティ制御」だが、5% の 1 段が 45km/h で 2.4 km/h/s あり、
**違反時間の 27.8〜37.1% を単独で作っている**（3-3 の機構 B）。

**案**:
1. **ベンチで実機のブレーキ不感帯を再測する**。同定値 5.0% は学習運転の BRAKE_HOLD 段から
   オンセット検出したもので、アクチュエータのストローク校正（`calibration_data`）の
   ゼロ点誤差が乗っている可能性がある。**機械的な遊びの実測が要る**（ユーザー立ち会い）。
2. 5% が実在するなら、**減速側の微調整はブレーキではなくアクセル側で行う**方針に倒す。
   アクセル不感帯は 0.5% と細かい。減速中に部分アクセルで減速度を緩める制御は
   第2ラウンドで `analytic_efforts` の低開度域ブレンドとして入れてあるので、
   **その権限（現在フェーズクランプで brake フェーズ中のアクセル介入が制限されている）を見直す。**
   実際 t=145.9-147.0 では brake フェーズ中にトリムが +3.8〜4.0% のアクセルを出しており、
   この経路自体は機能している。
3. エスカレーションのヒステリシス（現在は FAST_RELEASE 離脱まで保持）を、
   **予測される速度超過量が 5% ブレーキ 1 段の効果を上回るときだけ**起動する条件に変える。

**判定**: brake フェーズの p95 2.30 が drive フェーズ（1.24）と同水準に近づき、
**機構 B の違反時間 3.8〜7.1s が 1s 未満になること。**

### 優先 C — θ をサイクルごとの同定値ではなく安定した値に固定する

**問題**: θ が 0.30〜1.05s で暴れ、FB 権限・プラン前倒し・ILC リードの 3 つを同時に振り回す。
最大逸脱に対しては「速い補正層＝max≤1.0 の安全網」の権限が毎サイクル 2〜3.5 倍変わることが直接の害。

**案**:
1. 5 サイクル分の θ 実測（0.30/0.70/0.50/0.80/1.05）の**中央値 0.70s を車両定数として固定**し、
   同定値は参考記録に留める。あるいは同定値に前回値との指数移動平均をかける。
2. より根本的には、θ を「速度が 0.3km/h 上昇するまで」ではなく
   **アクセル開度ステップと加速度応答の相互相関ピーク**で測る（`scripts/` に解析を追加して
   既存の 5 サイクル分のログでオフライン比較できる。実機不要）。
3. θ を固定できれば、FB 権限・前倒し量が走行ごとに変わらなくなり、**ILC の学習対象が安定する**
   （現状は「毎回違う制御器で学習している」状態）。

**判定**: 連続 2 サイクルで stage1 kp と実効トリムゲインが ±20% 以内に収まること。

### 優先 D — ILC の採否を KPI 辞書順に揃える【p95 担当・工数小】

**問題**: ILC 採否 `plan_service._decide_outcome` は reward 単独で判定しており、
学習サイクル側の best 選択（第2ラウンドで「KPI 合否 → p95 → reward」の辞書順に修正済み）と
食い違っている。iter 12 は p95 1.43（サイクル最良）を出したが reward で捨てられ、
iter 13 でロールバックされ、**979fb2f5 は 3 本走って進捗ゼロで終わった。**

**案**:
1. `_decide_outcome` を **「KPI 合否 → p95 → reward」の辞書順**に揃える。
2. **報酬の超過積分の重み（10.0）は下げないこと。** 報酬の 89% がここなのは
   「max を最重視している」という意味で、PRD の優先度とは整合している。
   3-3 のとおり max が下がらないのは重み付けの問題ではなく ILC の操作対象の問題なので、
   **ここを緩めると max を守る唯一の圧力を失う。**
   p95 を効かせたいなら超過積分を弱めるのではなく、p95 項の係数だけ上げる。
3. 重みを変えると `reward_scale_key()` が変わり **best_reward は自動で再ベースラインされる**
   （`plan_service.py:334-344`）。既存 13 反復の履歴は残るが比較不能になる点に注意。

**判定**: 次サイクルで iter が 3〜4 本とも accept され、p95 が単調に下がること。

### 優先 E — 120km/h プラトーの 0.57Hz 変動の出所を切り分ける

**問題**: 制御に関係なく偏差 std 0.57〜0.72 km/h が乗っている。p95 0.4 の物理的な達成可能性に直結する。

**案**（実機ではなく計測の切り分け）:
1. **アクチュエータを一切動かさずに** 120km/h 定常をダイナモ側だけで維持し、CAN 車速を記録する。
   同じ鋸歯が出れば車速信号／ダイナモ側、出なければ我々のペダル操作が起点。
2. CAN の Speed シグナルの更新周期と分解能を DBC（`config/can/MEIDEN_MEIDACS.dbc`）で確認する。
   10Hz でログしているが CAN が 5Hz なら階段が出る。
3. 出所がダイナモ／計測なら、**KPI 閾値の再設定をユーザーと合意する**か、
   評価に使う車速だけに（制御には使わない）ゼロ位相フィルタをかける。
   ※制御用フィルタは第2ラウンドで害があると確認済みなので、**評価専用**に限ること。

**判定**: ペダル無操作時の 120km/h 定常で std がいくつになるか。

### 優先 F — 積み残し（第3ラウンドから継続）

| 項目 | 状態 |
|---|---|
| **本番モード（WLTP 等）の保存プランが 1 件も無い** | `pedal_plans` は `__verify_pattern__` の 1 行のみ。KPI 検証はすべて検証パターンで行っている |
| PID 仕上げフェーズ（`refine_final_runs=0`）が走っていない | 所要時間短縮のため 0 のまま |
| ILC リード時間の実測決定 | Δ=θ+0.5s は依然として暫定値。優先 A/C と一緒に扱う |
| S 字モーション（CTLF MOD=0,1）の採否 | ベンチ未実施 |
| ボーレート 38400 → 230400 | 未着手 |
| 滑らかさ KPI がゲートに入っていない | 記録専用のまま（ユーザー方針） |
| PCON-CB パラメーター No.152（高出力化設定）の実機値 | Modbus から読めない。IAI ティーチングソフトが要る。config は無効時の値で安全側 |

  アクセル／ブレーキアクチュエータが物理的に動き、シリアルポートを占有する。実機起動はユーザーが行う。
- **ポート 8080 が使用中なら、ユーザーが手動起動した実機接続インスタンスの可能性がある。**
  走行系 API を叩かない・kill しない。自分の検証は **8081** で立て、終わったら必ず止める。
- **本番 DB は読み取り専用。** 走行データへの UPDATE/DELETE は行わない。
- **第3ラウンドの変更は全部未コミット。** `git status` の差分が実機で走った状態そのもの。
  コミットはユーザーの明示指示があるときだけ。
- 一時ファイルはスクラッチパッドへ。プロジェクト配下に置かない。
- 「議論したい」と言われたら、いきなり Plan を作らず内容を深堀りしてから計画にする（CLAUDE.md）。
