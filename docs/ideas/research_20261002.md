### 1. 明電舎 JP2020148593A

モデルが 3 つある。順モデルは 1 つ目だけで、**開度を出すのは 2 つ目**。

| モデル | 入力 | 出力 | 役目 |
|---|---|---|---|
| 車両学習モデル（順モデル） | ある時刻までの過去の車速の列（長さ「第 1 時間」）＋その時刻から先のアクセル・ブレーキ操作量の列（「第 2 時間」） | その時刻から先の車速の列（「第 3 時間」） | 実車の代わりをするシミュレータ |
| 操作推論学習モデル | 走行状態（アクセル・ブレーキの検出量、車速、指令車速） | 先の「第 3 時間」ぶんのアクセル・ブレーキ操作の列 | 開度を決める。強化学習で作る |
| 価値推論学習モデル | 走行状態と操作 | その操作の良さ（行動価値） | 強化学習の採点役 |

| 項目 | 原文の内容 |
|---|---|
| 順モデルの構造 | 中間層 3 層・全 5 層の全結合ニューラルネット。ノード数・活性化関数は記載なし |
| 順モデルの学習 | 先の車速の列の実測を正解にして、平均二乗誤差を小さくする（誤差逆伝搬・確率的勾配降下）。誤差が所定値より小さくなったら終了 |
| 学習データの走り方 | 「車両特性計測用の操作パターン」で実車を走らせる。例として「**類似する他の車両が WLTC などを走ったときのペダル操作の実績値**」を使う、とある |
| 開度の決め方 | 順モデルを相手に強化学習（行動価値が高くなる操作を出すように学習、TD 誤差で価値側を学習）→ 終わったら相手を実車に替えて強化学習を続ける。終了条件はモード走行の車速誤差が閾値以下 |
| 変形例 | 入力にエンジン回転数・ギア状態・エンジン温度の列を足し、出力にもそれらの先の列を足してよい |
| 書かれていないもの | 第 1〜第 3 時間の秒数、制御周期、学習に要る走行時間、追従精度の数字、強化学習のアルゴリズム名、報酬の式 |
| 請求項 1 の骨子 | 「実車の走行実績で機械学習した車両学習モデル」＋「その出力で操作推論学習モデルを**事前に強化学習**」＋「その後、**実車で更に強化学習**」の 3 つがそろった学習システム |
| 状態 | Google Patents の表示は Pending。登録の有無は未確認のまま |

- **順モデルを逆に引いてはいない。** 順モデルは「車速の列」を返すので、表のように逆引きできない。開度を出すために別のモデルを強化学習で作っている
- 学習データの走り方（モードに近いペダル操作）は、ProblemReport_20261001 段2e の事実 3（手順2 のステップ走行で覚えると外れ p95 0.44、WLTP のログで覚えると 0.25 km/h/s）と同じ向き

### 1b. 明電舎 US11718295（請求項 1 と要点のみ）

- 操作推論モデルの入力: アクセル・ブレーキの検出量、エンジン回転数、車速、指令車速（過去の観測の列と、先の指令車速の列）。出力: 先の複数時刻のアクセル・ブレーキ操作の列
- 推論の周期は制御周期より長い。過去 M 回の推論から「次の制御時刻」の操作を取り出し、重み α_i = (1/x)^i ÷ 合計（x > 1。新しい推論ほど重い）で足す。x は実験で決める
- **順モデルは使っていない**（強化学習の採点役のモデルだけ）。順モデルの議論の材料にはならない

### 2. Baidu Apollo 自動キャリブレーション（arXiv 1808.10134）

**表の向き**: 学習は「アクセル／ブレーキ指令・車速 → 加速度」（順モデル）。使うときは `T[指令][車速] = 加速度` を `[車速][加速度] = 指令` に並べ替えて引く（原文の擬似コード 2 の 12 行目）。指令は 1 本の軸（付録の図では −50〜−15 がブレーキ、0〜90 がアクセル）。

**走る前の表の作り方（オフライン）**

| 項目 | 原文の内容 |
|---|---|
| データ | 人が運転した走行データ約 20 分。特徴量は 指令・車速・前後加速度（慣性センサ）。**アクセルとブレーキは別々のモデル** |
| 前処理 | 移動平均で平滑化／ハンドル角が大きい行は捨てる／**車速 × 指令のマスごとに行数をそろえる**（データの偏りをならす）／マスの中で平均から標準偏差 1 つぶん以上離れた行は捨てる |
| モデル | 3 層のニューラルネット（活性化はシグモイド、損失は平均二乗誤差）。このモデルから表を作る |
| 他のモデルとの比較（10 分割交差検証、加速度の平均絶対誤差。アクセル／ブレーキ） | 線形回帰 0.465／0.472 m/s²（**1.67／1.70 km/h/s**）、ガウス過程 0.464／0.477、SVM 0.465／0.471、モデル木 0.230／0.230、ランダムフォレスト 0.154／0.140、**ニューラルネット 0.113／0.141 m/s²（0.41／0.51 km/h/s）** |
| 表の性質 | 指令 → 加速度、車速 → 加速度ともほぼ単調（図 2） |

**走行中の表の直し方（オンライン）**

| 項目 | 原文の内容 |
|---|---|
| 遅れの扱い | 指令を出してから **200 ms 後**の加速度を、その指令の結果とみなす。加速度は 3 次のバターワース低域フィルタ（遮断 2 Hz） |
| 使う行の条件 | (a) 自動運転中でハンドル角が小さい (b) **その指令の前後 100 ms に指令がほとんど動いていない**（式 6）(c) (基準車速 − 実車速) と (要る加速度 − 実加速度) が同じ符号（式 7） |
| 直さない条件 | 車速の偏差が閾値以下なら、その周期は表を触らない（式 8） |
| 直す量 | 差 ＝ 要る加速度 − 実加速度。各マスを Δ ＝ 差 × 学習率 ÷（1 ＋ コスト）だけ動かす。コストは「今の指令・車速から遠いマスほど大きい」×「初期の表を保つ項」。周りのマスも距離に応じて少し動く |
| 守る制約 | 指令に対する加速度の単調性（式 5。逆に引けなくならないため） |
| 計算量 | 100 Hz で毎周期更新、1 回 2 ms 未満（産業用 PC）。オフラインの表作りは 10 秒未満 |

**結果**

| 条件 | 車速の平均絶対誤差 |
|---|---|
| Lincoln MKZ（ハイブリッド）、オフラインの表のみ、30 分 × 10 回、最高 10 m/s（36 km/h） | 0.145 m/s（**0.52 km/h**）。手動で較正した表は 0.144 |
| Neolix AX1（電動の配送車、最高 3 m/s）、積載 300 kg、オンラインなし → あり | 0.149 → 0.102 m/s（0.54 → 0.37 km/h） |
| 同、積載 0 kg | 0.126 → 0.118 m/s（差はほぼ無い） |

- この誤差は**フィードバックつきの制御**での値（下の 2b）。FF のみの数字は載っていない
- オンラインの直しが効いたのは積載を変えたとき（車の特性が変わったとき）。特性が変わらなければ効果は小さい

### 2b. Apollo の制御の式（arXiv 2011.04250）

```
要る加速度 a_cmd = 基準の加速度 a_ref + Kp_v ×（車速の偏差 + Kp_x × 位置の偏差）+ Ki_v × 同じものの積分
開度 u = 表（a_cmd, 車速）
```

- 基準の加速度（先読みしたもの）がそのまま表に入る部分が FF。偏差は**開度ではなく「要る加速度」に足す**。フィードバックの強さは Kp_v・Ki_v・Kp_x の数字で決まる（高速用と低速用の 2 組）
- ProblemReport_20261001 段2e の「開度の出し方 a」（偏差 1 km/h あたり k km/h/s を要る加速度に足す）は、この式の Kp_v だけを使った形。段2e で「原典を読んでおらず記憶に基づく」としていた点は、原文で確認できた
- この論文での表: 入力 2 つ（アクセルまたはブレーキ指令・今の車速）→ 次のサンプルの加速度。隠れ層 1 つ（シグモイド）の小さなニューラルネットで、「駆動部の遅れを織り込む」とある（方法の詳細は記載なし）。データ収集と学習で約 2 時間
- 同じ論文に、別の順モデルがある: LSTM（過去 20 ステップの アクセル・ブレーキ・ハンドル・車速・加速度 → 次の加速度。隠れ 8 次元）。これは**ゲイン調整用のシミュレータ**に使うもので、開度は出さない。明電舎の車両学習モデルと同じ役目

### 2 つを並べる

| | 明電舎 | Apollo |
|---|---|---|
| 順モデルの入力 | 過去の車速の列＋先のペダルの列 | 今の車速＋今のペダル（1 点） |
| 順モデルの出力 | 先の車速の列 | 加速度（1 点） |
| 開度の出し方 | 別のモデルを強化学習で作る | 表を逆に引く＋偏差を要る加速度に足す |
| 順モデルの役目 | シミュレータ（実車の代わり） | FF そのもの |
| 履歴で決まる現象（遅れ・ヒステリシス）の扱い | モデルの入力に列で持つ | 持たない。遅れは 200 ms ずらして合わせ、指令が動いている行は直しに使わない |
| 計算の重さ | ニューラルネット 3 つ＋強化学習 | 表引きのみ。更新は 2 ms 未満 |
| 示されている精度 | 記載なし | フィードバックつきで平均 0.37〜0.52 km/h（36 km/h 以下） |

Apollo 自身も、シミュレータ用には明電舎と同じ「履歴つきの順モデル」（LSTM）を別に持っている。つまり 2 つは対立する方式ではなく、**「開度を出すための順モデル」は 1 点 → 加速度、「走りを再現するための順モデル」は列 → 列**、と役目で使い分けられている。

## 明電舎型と Apollo 型のどちらを採るか（Claude 意見 2026-10-02。未決定）

**推奨: 開度を出す順モデルは Apollo 型（車速 × 開度 → 加速度）。明電舎型は「車速の列で採点する」考え方だけ借りる。**

| # | 理由 | 根拠 |
|---|---|---|
| 1 | 「表を逆に引いて、走る前に開度の列を作る」ができるのは Apollo 型だけ | 明電舎型は出力が車速の列で、入力が先のペダルの列。逆に引けないので、明電舎は強化学習、他は毎周期の最適化（MPC）で開度を出している。どちらも実車速を見るフィードバックを中に含み、強さが数字で見えない（C5 のばたつきと同じ構造） |
| 2 | 今の実車データでは、履歴を入力に足しても精度がほとんど変わらない | ProblemReport_20261001 段2e 事実 3: 過去 4 秒の開度・車速を足して 0.25 → 0.22 km/h/s（p95）。学習データの走り方を替えるほう（0.44 → 0.25）が効いた。決定木 1 種類・検証 1 本の試算で、採否を決めるものではない |
| 3 | 30 分の学習・ラズパイでの学習に収まる | Apollo は 20 分のデータ・表作り 10 秒未満。明電舎型は順モデルの後に強化学習（模擬＋実車）が要り、時間の記載が無い |
| 4 | 特許の中心から離れる（推測。弁理士の確認は要る） | JP2020148593A の請求項 1 は「操作を推論するモデルを事前に強化学習し、実車で更に強化学習」が要素。表を逆に引く方式にはこの要素が無い |

**Apollo 型をそのまま持ち込めない点**（どれも要検討）

| # | 点 | 何が困るか |
|---|---|---|
| 1 | Apollo の精度は KPI に届いていない | フィードバックつきで平均 0.52 km/h。こちらの KPI は p95 0.4・最大 1.0 km/h で、平均ではなく上側を見る。**Apollo の論文は「この形で KPI に届く」ことの裏付けにはならない** |
| 2 | 線形回帰は Apollo では最下位（ニューラルネットの約 4 倍の誤差） | 「次はモデル（線形回帰・Ridge）」の段は、車速と開度をそのまま入れるだけだと同じ結果になる見込み。車速² ・開度² ・車速 × 開度 の項を入れること、アクセルとブレーキを別の式にすることが前提になる（Apollo も別々） |
| 3 | Apollo は「指令が動いている行」を直しに使わない | WLTP ではペダルが動いている時間が 72%（段2e 事実 6）で、外れが出るのもその間（事実 5: 踏み増し中 +0.14 km/h/s）。同じ条件で行を捨てると、一番直したい場面が表に入らない。**動いている行も使う／向き（踏み増し・戻し）を軸に足す**、のどちらかが要る |
| 4 | 表は軸にしたものしか区別できない | ブレーキの「山から戻すと効きが半分」（段2b）、HEV のエンジン始動、EV の回生は、車速 × 開度の 2 軸では同じマスに混ざる。ここが足りなくなったときが、履歴つき（明電舎型）に進む場面 |
| 5 | 逆に引けるには、開度に対して加速度が単調でなければならない | マスの平均をそのまま使うと、データの少ないマスで逆転が起きる。Apollo は単調性を制約にしている（式 5）。不感帯（アクセル 4.21%・ブレーキ 7.26%）の中は加速度が変わらないので、そこは引けない区間として別に扱う |
| 6 | 遅れのずらし量 | Apollo は一律 200 ms。こちらの実測はアクセル約 0.30 s（格子ステップ `155259`）、ブレーキは先読み 0 s で踏み始めが合った（段2）。表を作るときに開度と加速度を何秒ずらすかを、アクセル・ブレーキ別に決める |

**出力は加速度か車速か**

- 1 点の順モデルの出力は**加速度**にする。車速を出力にすると「今の車速とほぼ同じ値」を当てるだけで誤差が小さく見え、効きの外れが数字に出ない（0.05 秒先の車速は、加速度 1 km/h/s の外れでも 0.05 km/h しか違わない）
- **車速の列は採点に使う**（明電舎の学習の仕方を借りる）: 別の走行ログの実開度を順モデルに入れ、加速度を積み上げて車速の列を作り、実車速と比べる。FF の偏差は区間ごとの外れの積み上がりなので（ProblemReport_20261001）、1 点ごとの加速度の誤差より、この積み上げた車速のずれのほうが実機の偏差に近い

**ユーザーの進め方（表 → モデル → 表＋モデル）への意見**

| 段 | 意見 |
|---|---|
| ① 表のみで実機 | 賛成。先に決めること: マスの刻み／データの無いマスの埋め方（表だけで走るにも要る。となりのマスから補間するか、今の較正の式に戻すか）／単調にそろえる方法／ずらす秒数／どのログで表を作るか（手順2 のみ・WLTP のログ込み） |
| ② モデルのみ | 上の「持ち込めない点 2」のとおり、2 次の項・アクセルとブレーキ別が前提。今の較正の式（惰行の加速度(車速) ＋ 感度(車速) ×（開度 − 不感帯））は、係数について線形なので Ridge でそのまま当てはめられる |
| ③ 表＋モデル | Apollo の形（モデルで全マスを埋めて表にする）と、段2e の「土台の式＋補正の表」（モデルを土台にして、実測との差だけを表で持つ）の 2 通りがある。後者はデータの無いマスが自動で土台に戻る |
| 走行中に表を直す（Apollo のオンライン） | 最初は入れない。Apollo で効いたのは積載を変えたときで、暖機済みで再現する車（同じ指令で p95 0.60 km/h。段2e 事実 1）には、走行の合間に表を作り直すほうが単純。「本番走行を収束の場にしない」方針とも合う |
| フィードバック | Apollo の式（偏差 × Kp を要る加速度に足して表を引き直す）を、①の FF のみの実機の後に足す。強さは 1 つの数字で、実機で上限を決める |

**決めたい分岐**（ユーザー判断）

1. 開度を出す順モデルを Apollo 型（車速 × 開度 → 加速度）で始めるか
2. 表の軸に「向き（踏み増し・戻し）」を最初から入れるか、2 軸で走ってから足すか
3. ①の表を作るログ（手順2 のみ／WLTP の実走ログ込み）

## 特許の整理（明電舎）

Claude は弁護士・弁理士ではない。以下は一般的な整理で、判断は知財部門か弁理士に確認する。

### 基本

| | 守るもの | 自分でコードを書けば避けられるか |
|---|---|---|
| 著作権（オープンソースのライセンス） | コードの書き方そのもの | 避けられる |
| 特許 | 「請求項」に書かれた仕組み | **避けられない**。同じ仕組みなら誰が書いても対象 |

- 特許を**読むこと・参考にすること**は問題ない（公開する代わりに独占権を得る制度）
- 侵害になる条件（日本）: 「業として」、登録された特許の請求項の**全部の要素**を満たすものを作る・使うこと。1 つでも要素が欠ければ対象外
- **社外に出さない自社内の利用でも「業として」に当たる**（事業のための利用は、販売しなくても対象。個人の趣味・家庭内の利用だけが外れる）。今回は業務用なので、特許の確認が要る
- 試験・研究の例外（特許法 69 条）は、その特許発明自体を試す・改良するための研究が対象。業務の道具として使うことまでは含まないとされる
