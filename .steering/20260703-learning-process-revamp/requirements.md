# 要求内容

## 概要

学習運転プロセス(学習運転→モデル訓練→PID適合)を見直し、①学習サイクル単位のログ統合、②特徴量の設定可能化とオフライン評価、③2段階学習フローの全自動オーケストレーションを実現する。

## 背景

現行フロー「学習運転(開ループ)→最新学習ログで訓練→規定パターン最大15回でPID適合」には以下の課題がある:

1. **ログ分断**: 学習運転1件 + PID適合走行ごとに1件の `drive_sessions` が作られ(15回なら計16件)、1回の学習サイクルのログがDB/UI上で散らばる。学習データの選択・履歴の把握が煩雑
2. **特徴量の妥当性が未検証**: 現在の9特徴(`v0, dv_0.5, dv_1.0, dv_2.0, dv_3.0, v0², dv_1.0×v0, dv_past_0.5, dv_past_1.0`)が最適か不明。人間のドライバーは現在車速と複数の未来車速を繋ぎ合わせてペダル開度を決めることから、短期未来(0.1/0.2/0.3秒先)や加速度項の追加候補がある。ただしホライズン定義がコード内に散在(`model_training.py` のモジュール定数を `feedforward.py` が直接参照)しており、候補比較の実験ができない
3. **1段階学習の限界**: 学習運転(開ループ掃引)のログだけで訓練するため、規定パターン域の走行データが活きていない。PID適合の閉ループ走行ログも「その開度でその速度が実現した」という逆モデルの正当な学習データであり、これを使った再学習で精度向上が見込める

## 実装対象の機能

### 1. 学習サイクルによるログ統合(サイクルID紐付け方式)

- `learning_cycles` テーブルを新設し、`drive_sessions.cycle_id` で学習運転〜PID適合の全セッションを1サイクルに紐付ける
- 学習運転開始で新サイクルを開設、以降の適合走行は同一サイクルに参加。manual/通常autoは `cycle_id NULL`
- PID適合走行の `run_type` を `'auto'` から `'tuning'` に分離(通常自動走行と区別可能に)
- UI(ログ画面)はサイクル単位でグループ表示、学習データ選択も「1サイクル=1件」扱い
- 走行単位のセッション分割は維持する(走行ごとのKPI評価・特徴量の先読みがセッション境界を跨がない性質を保つため)

### 2. FeatureSpec による特徴量の設定可能化 + オフライン評価

- 特徴量構成(先読みホライズン・過去ホライズン・加速度項・二次項)を `FeatureSpec` dataclass で定義可能にする。デフォルトは現行9特徴と完全一致
- 学習時の `FeatureSpec` を pkl に保存し、推論側(`FeedforwardController`)はpklから復元した spec で特徴を構築する(現状はモジュール定数をハードコード参照しており、pkl内のホライズン情報は読まれていない)
- オフライン評価スクリプト `scripts/evaluate_feature_sets.py` を新設し、既存ログで候補特徴量セット(短期未来0.1/0.2/0.3秒・加速度項など)をA/B評価する
- 本番の特徴量セット変更は評価結果を確認してから実施する(このステアリングでは評価基盤の構築まで。9特徴からの変更自体はスコープ外)

### 3. 2段階学習フローの全自動オーケストレーション

- 新フロー: 学習運転 → モデル訓練+SIMC初期ゲイン → PID適合(最大10回) → **サイクル全ログで再学習**(ゲイン上書きなし) → PID適合(最大5回、1段目ゲインから継続)
- WebUIの1操作(「学習サイクル開始」ボタン)で全フェーズを自動進行。進捗はWebSocketでリアルタイム表示
- いつでも中断可能。中断・エラー時は必ずブレーキ解放し、サイクル状態を記録
- 適合回数(10/5)は設定・リクエストで変更可能
- 既存の個別API(`/learning/train`, `/pid-tune/refine` 等)は手動パスとして維持

## 受け入れ条件

### 学習サイクルによるログ統合
- [ ] 学習サイクル実行後、`GET /api/v1/sessions/cycles` で学習セッション+全適合セッションが同一 `cycle_id` で取得できる
- [ ] ログ画面で1サイクルが1つの折りたたみ項目として表示される(manual/通常autoは従来どおりフラット表示)
- [ ] PID適合走行のセッションが `run_type='tuning'` で記録される
- [ ] `/learning/train` に `cycle_id` を指定するとサイクル内全セッションのログで訓練できる
- [ ] サーバー再起動時に走行中のまま残ったサイクルが `error` で回収される

### FeatureSpec + オフライン評価
- [ ] デフォルト `FeatureSpec` の特徴名・値が現行9特徴と完全一致する(回帰テストで固定)
- [ ] 訓練したpklに `feature_spec` が保存され、推論側がそれを復元して特徴構築する
- [ ] 旧 `model_type` のpklはロード時に拒否される(再訓練を強制)
- [ ] `scripts/evaluate_feature_sets.py` が既存サイクルのログで候補セットのin-sample/holdout指標を出力する
- [ ] holdout評価に「実速度から特徴構築」と「基準速度(ref_speed_kmh)から特徴構築」の両方が含まれ、その差が確認できる

### 2段階フロー オーケストレーション
- [ ] WebUIの1操作で 学習運転→訓練→適合(10)→再学習→適合(5) が自動進行し、完了後にREADYへ戻る
- [ ] 2段目の再学習で `profile.pid_gains` がSIMC解析値で上書きされない(1段目の適合結果が保持される)
- [ ] フェーズ間(学習終了〜訓練〜1段目適合〜再学習〜2段目適合)を通して車両が停車保持ブレーキで静止し続ける
- [ ] 中断操作で走行が安全に停止し、ブレーキ解放・サイクル状態 `aborted` が記録される
- [ ] フェーズ・走行回数(i/N)・最良コストがWebSocket経由でUIに表示される
- [ ] オーケストレーション実行中に旧クライアント側自動チェーンが発火しない(旧チェーンは削除)

## 成功指標

- 学習サイクル1回の操作数: 現状3操作以上(学習開始→訓練→適合) → 1操作
- 1サイクルのログがUI上1項目に集約される(現状16項目前後)
- 2段階学習後の自動運転KPI(P95偏差 0.2 km/h以内、最大偏差 1.0 km/h以内)の達成率が1段階学習と同等以上(実機検証で比較)

## スコープ外

以下はこのフェーズでは実装しません:

- 本番特徴量セットの9特徴からの変更(オフライン評価の結果を見て別途判断)
- GBM等の木モデル再導入(20260630で棄却済み: オフマニフォールド飽和により巡航追従が破綻)
- 物理的に1セッションへ統合する方式(サイクルID紐付けで代替)
- 3段階以上の反復学習ループの一般化(2段固定。将来拡張はdesign.mdで考慮)
- 過去の既存セッション(`cycle_id NULL`)への遡及的なサイクル付与
