### 考え方として
- 発進
    徐々にブレーキを離していって、クリープ車速を出す
- 加速
    クリープ車速で走れるところはクリープで走り、足りない部分はペダル操作で加速する
- 定常
    なるべく開度は一定に保つ
- 減速
    アクセルを緩めて減速するシーンはアクセルを緩めていく
    ペダル操作なしで惰行で減速できるところはなるべくペダル操作なしで減速
    ブレーキ減速が必要なシーンはブレーキで調整して、バタバタペダル操作しない
- 停止
    一度踏んだら戻したりバタバタしないで、徐々に踏み増して減速して停止させる
- 全体として
    バタバタペダル操作するような運転しない
    なるべく開度は一定に保つ
    操作しないで運転できるところはペダル操作しない

### 段2 で直す内容

現行のペダル選択は 1 本の不等式（`要求加速度 >= 惰行加速度` ならアクセル、下ならブレーキ）で、**「どちらのペダルも使わない」という出力が存在しない**。この車は 10〜30 km/h の惰行減速（−4.8〜−7.2 km/h/s）が WLTP の要求減速とほぼ一致するため差がゼロ付近に張り付き、C5 は v0 に実測車速を使うのでその揺れが毎周期符号を変える。

C5 の WLTP 走行（`drive_log_real_20260916_141206.csv`）の t=90.0〜93.2s では **3.2秒で10回入れ替わっている**。そのときの指令はアクセルが毎回きっかり不感帯（10.00%）、ブレーキが不感帯のすぐ上で、FF は「ほとんど何も要らない」と言いながら、どちらのペダルで何も要らないかを言い直し続けている。1800秒あたりの入れ替わりは **C5 = 130回、C1 = 18回**（課題#3 は C5 の構造から出ている）。

対策は、判定の「点」を「帯」にすること:

```
if |要求加速度 − 惰行加速度| < ε:  両ペダルとも待機位置（＝惰行）
```

- **ε = 0.5 km/h/s**（`feedforward.coast_band_kmhs`）。0.3 では帯が薄すぎて端でバタつき、0.8 以上は帯にいる間のドリフトが KPI の最大逸脱 1.0 km/h を超える
- **ヒステリシスは入れない**（1変数比較を保つ。実機で問題が出たら次に入れる）
- 旧「クリープ任せ」分岐（`0 ≤ 要求加速度 ≤ creep_rate_kmhs(0.23)` の幅0.23の窓）は帯に吸収して削除する。段1の実測では 1 km/h 地点の実クリープ加速度が 1.5 km/h/s で、この窓はほぼ発火していなかった（＝課題#2 の直接原因）

既存ログ上の試算では、アクセル⇔ブレーキの直接入れ替わりが C5 で 106 → 21 回、発進域（v<2km/h・加速要求）で惰行が選ばれる時間が C5 = 2.5s / C1 = 5.7s（現行はいずれも 0s）。

**注意**: 3状態（アクセル／惰行／ブレーキ）の遷移で数えると C1 は 34 → 51 と増える。A↔B の1回が A→惰行→B の2回に割れるため。判定は「アクセル⇔ブレーキの直接入れ替わり」と「1周期あたりの開度変化量」で行う。

### 段2.5: 低速の惰行カーブ（2026-09-18）

C5 の 1 km/h 超え 29.4s のうち **29.0s が基準 0〜20 km/h 帯**。その低速域で、段2・段3・段4 が共通の土台にする
`free_accel_at`（今ペダルを離したときの加速度）が実測と合っていなかった。

手順3 の惰行区間（両ペダルが実際に待機位置へ収まった行だけ、16 区間）と模型の比較:

| 速度帯 | 実測 [km/h/s] | 模型 | 差 |
|---|---|---|---|
| 0.7〜1.9（クリープ） | +1.26〜+1.54 | +1.27〜+1.51 | ±0.04 |
| 9〜18（惰行） | −2.70〜−4.78 | −3.11〜−4.69 | −0.18〜+0.41 |
| **5.0〜6.5** | **0.00 / −0.35 / −0.76** | **−2.23 / −2.27 / −2.39** | **+1.6〜+2.2** |

原因は本番推定器のビン幅。`src/domain/model_training.py:456` の `COAST_CURVE_BIN_KMH = 10.0` が
0〜10 km/h を 1 ビンにまとめ、その中央値をビン中心 5.0 km/h に置くため、**5〜10 km/h が
すべて 2.235 という 1 本の値**になっていた。さらに惰行サンプルは `sp > creep_speed_kmh` で採るので、
模型の `free_accel_at` は `v=4.79 → +0.10` から `v=4.80 → −2.235` へ **1 ステップで 2.3 km/h/s 飛ぶ**。
物理的には、クリープ平衡速度はまさに惰行加速度が 0 になる速度なので 0 を通らなければいけない。

実害: C5 の 2 番目に大きい逸脱がこれ。t=96.1s、5.29 km/h で「惰行すれば −2.27 で落ちる」と判断して
両ペダルを離したが実車は 0.85 秒 5.00 km/h に張り付き、基準が 3.4 km/h まで下がって **+1.75 km/h**。
惰行帯 ε=0.5 km/h/s に対してこのずれは 3〜4.5 倍ある。

### 段4 の当初実装（2026-09-18）と、その 2 つの仕様ミス

当初は「その速度から停車まで持っていくのに必要な開度」を**速度のカーブ**として持ち、停止到達側は
下限・発進側は上限でクランプする設計にした。手順2 の実機走行で、この設計が測っているものが違って
いたと判明した。

**誤り 1: 速度軸の取り方が構造的に間違っていた。** 1 点を「停止する 1 行前の車速」と定義したが、
車は減速しながら止まるのでその車速は必ず 0 付近になる。2026-09-19 の走行の停止イベント 45 件
すべてで 0.03〜1.19 km/h だった。**定義上 0〜1.25 km/h より上には点が出ない。** 4 km/h 側の情報は
「その保持が停止に到達した」という事実の側にあり、旧仕様はそれを捨てていた。

**誤り 2: 開度が高めに偏っていた。** 45 件のうち 43 件は停止確認の刻み送り（0.5 mm / 1 s）中の停止で
23.35〜28.32% と記録される。これは「止まるのに必要な開度」ではなく「停止判定の瞬間に刻みがどこまで
進んでいたか」で、境界 18.3% より 5〜10% 深い。ビン中央値がこの群に支配された。

結果、手順2 が保存したカーブは `[0.0, 0.25, 0.75] → [28.32, 25.558, 26.551]` で、0.75 km/h 以上は

止まりすぎるので、`brake_trim_max_kmh: 0.0`（無効）のまま破棄した。

なお実機走行の**前**にも仕様ミス 2 件を検出して直しており（ビン内の統計量に最小を指定していた件・

定数化によってどちらも消える（向きの場合分けそのものが不要になる）。

### 段4 改訂: クリープ域ブレーキの下限（2026-09-19）

対策は**カーブではなく定数 1 本の下限**。「基準が止まりかけているあいだ、ブレーキを実測の停止境界
より浅くしない」。境界に速度依存はほとんど見えない（0.33 km/h でも 4.95 km/h でも 17.8〜19.8% の
同じ帯）ので、カーブにする根拠が無い。**停止側と発進側が同じ規則になる** — どちらも「基準がまだ
0 付近なのに境界を割っている」状態だから。開度変化率の制限（レートリミット）は設けない（人間の
運転にその制限は無い、というユーザーの方針）。この下限は速度と基準の関数で、時間の関数ではない。

規則（`ff_candidate._apply_brake_trim`）:

```
brake_trim_max_kmh <= 0.0            → 何もしない（既定。現行と完全に同じ経路）
stop_brake_floor_offset_pct <= 0.0   → 何もしない（未同定）
v0 > brake_trim_max_kmh              → 何もしない
ref_next > brake_trim_ref_kmh        → 何もしない（基準が動き出したら解放する）
それ以外 → opening = max(opening, brake_deadband_pct + stop_brake_floor_offset_pct)
```

#### 残る段差について（指標の定義を直す）
