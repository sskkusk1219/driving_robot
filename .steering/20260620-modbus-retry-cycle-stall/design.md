# 設計書

> **実装結果による更新（2026-07-06）**: 本設計は当初「timeout/retries の調整」を
> 主対策と想定していたが、実機検証で timeout 調整は無効と判明した。確定した根本原因は
> **P-CON-CB が FC16 書込直後の FC03 読取に対して初回応答を欠落させる**こと（brake 軸で
> 顕著、accel 軸でも低頻度）で、有効だった対策は `DriveLoop` の各軸駆動で
> `move_to_position` → `read_current` の間に **10ms の待機（`AXIS_PRE_READ_DELAY_S`）を
> 挿入する**ことだった。原因・棄却仮説・実測効果の総括は `tasklist.md` 冒頭の
> 「確定した原因と対策（総括）」を参照。

## アーキテクチャ概要

調査 → 計測 → 切り分け → 対策の順で進める。コード変更は実機での計測結果に基づいて
最小限に行う（推測でタイミング定数を変えない）。

```
[計測] drive_loop のサイクル所要時間 / スキップ警告
       actuator_driver のトランザクション所要時間・再送回数（pymodbus DEBUG）
   ↓
[切り分け] どの軸・どのトランザクションが、いつ、なぜ再送するか
   ↓
[対策] timeout/retries・再送戦略の調整（desync 回復を維持したまま）
   ↓
[検証] 実機 WLTP_ExHi 再走行でストール件数・ログ取得率を比較
```

## コンポーネント設計

### 1. 計測ハーネス（`src/infra/actuator_driver.py` / `src/domain/control/drive_loop.py`）

**責務**:
- トランザクション単位の所要時間と再送回数を記録する。
- サイクル単位の所要時間とスキップ発生を記録する（既存のスキップ警告ログを活用）。

**実装の要点**:
- pymodbus のロガー（`pymodbus.logging`）を DEBUG に上げて再送を可視化、または
  `_bus_op` をラップしてトランザクション開始〜完了の経過時間と結果（成功/タイムアウト）を
  計測する一時的な計装を入れる。
- 計装は走行性能に影響しない範囲（ログ I/O は非同期/間引き）で行う。
- 既存の「前回の制御サイクルが…スキップ」警告（`drive_loop.py:225`）の発生時刻を
  CSV ギャップと突き合わせる。

### 2. タイミング調整（`src/infra/actuator_driver.py`）

**責務**:
- 制御ループ中の Modbus トランザクションのタイムアウト/再送方針を最適化する。

**実装の要点**:
- 候補: `timeout` を実測の応答時間分布に合わせて調整、`retries` の段数や
  リトライ間バックオフの見直し、制御ループ用と初期化用で設定を分ける等。
- desync 対策（`_flush_input_buffer` + `_bus_lock`、retries による単発遅延からの回復）は
  維持する。retries を下げる場合はフラッシュ機構との整合を必ず確認。
- 変更は定数/コンストラクタ引数レベルに留め、制御ループ構造は変えない。

## データフロー

### ストール計測
```
1. 1 サイクル開始（_execute_one_cycle）
2. accel/brake トランザクションの所要時間・再送回数を記録
3. サイクル所要時間を記録、>interval ならスキップ警告
4. 走行終了後、ギャップ分布・ストール件数・累積時間を集計
```

## エラーハンドリング戦略

既存方針を踏襲（タイムアウト/通信失敗時は再送 → それでも失敗なら緊急停止）。本作業で
再送方針を変える場合も、最終的な失敗時に非常停止へ倒す経路は維持する。

## テスト戦略

### ユニットテスト
- `actuator_driver` のタイムアウト/再送設定変更がトランザクション挙動に与える影響を
  モック Modbus クライアントで検証（再送回数・例外伝播）。
- 既存テスト（`tests/unit/infra/test_actuator_driver.py`）のリグレッションがないこと。

### 統合テスト / 実機検証
- 実機 RS485 + IAI コントローラで WLTP_ExHi を 1 本走行し、
  CSV ギャップ分布・ログ取得率・ストール件数を変更前後で比較。
- desync カスケードが再発しないこと（長時間走行で恒久失敗が出ない）。

## 依存ライブラリ

新規追加なし（pymodbus / pyserial の既存設定を調整）。

## ディレクトリ構造

```
src/infra/actuator_driver.py        # timeout/retries・計装の調整
src/domain/control/drive_loop.py    # （必要なら）ストール計測の計装
tests/unit/infra/test_actuator_driver.py  # 設定変更のテスト
```

## 実装の順序

1. 計測ハーネス/ログ計装を入れて再送トランザクションを特定
2. 実機計測で初回タイムアウトの主因を切り分け
3. 切り分け結果に基づき timeout/retries・再送戦略を調整
4. 実機再走行で効果を検証（ギャップ件数・ログ取得率）
5. 計装の後始末（恒久ログに残すものと外すものを整理）

## セキュリティ考慮事項

- なし（ローカルバス通信のタイミング調整）。

## パフォーマンス考慮事項

- 計装ログが 50ms ループの予算（サイクル所要 < 50ms）を圧迫しないこと。
- タイムアウトを下げすぎると false timeout が増え、かえって再送が増える可能性があるため
  実測分布に基づいて決める。

## 将来の拡張性

- トランザクション所要時間の常時メトリクス化（WS/ログ）で、走行中のバス健全性を
  オンライン監視できるようにする余地がある（本フェーズ対象外）。
