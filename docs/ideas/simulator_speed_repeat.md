# シミュレータの車速が約 1.3 秒ごとに 1 周期止まる（読みの跳ね）

作成: 2026-10-29（Claude）。`ProblemReport_20261028.md` で「29 日以降に別に直す」とした「読みの跳ね」の中身をまとめたもの。

## 1. 現象

- **何が起きるか**: 加速・減速の途中でも、ロボットが受け取る車速が 1 周期（50 ms）だけ前と同じ値になる。次の周期からはふだんどおりの幅で進み、取り返す大きな一歩はない
- **どのくらいの頻度か**: 約 1.25〜1.35 秒に 1 回。周期的に起きる（ばらばらには起きない）

実際の例（`drive_log_real_20261029_042914.csv`、アクセル 25% で加速中）:

| elapsed_s | 基準車速 | 実車速 | 前の周期との差 |
|---|---|---|---|
| 21.083 | 57.967 | 57.709 | +0.165 |
| 21.132 | 58.119 | 57.908 | +0.199 |
| 21.183 | 58.275 | 58.073 | +0.165 |
| **21.231** | 58.425 | **58.073** | **0.000** ← 止まる |
| 21.282 | 58.577 | 58.238 | +0.165 |
| 21.326 | 58.733 | 58.402 | +0.164 |

## 2. 実測値

10 km/h 以上で加減速している行（10 周期で 0.5 km/h/s 以上変化している所）だけを数えた。

| ログ | 加減速中の秒数 | 同じ値が来た回数 | 1 秒あたり | 次に同じ値が来るまでの間隔（中央値） |
|---|---|---|---|---|
| `20261028_150414`（WLTP） | 1028 s | 921 回 | 0.90 回/s | 1.35 s |
| `20261029_042914`（約 600 s の走行） | 377 s | 352 回 | 0.93 回/s | 1.25 s |

- ロボットの制御周期は、平均 50.00 ms（ばらつき 31〜69 ms）
- 1 周期の変化量を、前後の平均の傾きで割った比は、ほとんどが約 1（69〜76%）。約 0（止まる）が 5〜7%、約 2（取り返し）は 2〜3% しかない → 「止まった後に跳ぶ」のではなく「止まって、そのまま遅れが 1 周期分リセットされる」

## 3. なぜ起きるか（推測。raspi3b 側ではまだ確かめていない）

シミュレータ（`~/projects/driving_simulator` のコピー、`defefd3`）の作りから、こう考えている。

| 部分 | 周期 | 決めているもの |
|---|---|---|
| 車速の計算（`speed_predictor.py`） | 10 ms | `PREDICT_STEP_S = 0.01` |
| CAN フレームの送信（`can_transmitter.py`） | 正確に 50 ms | カーネルの BCM（`send_periodic(msg, 0.05)`） |
| 送信するデータの書き換え（`send_loop`） | **50 ms ＋ 処理時間** | `await asyncio.sleep(0.05)` の後に `modify_data()`・sysfs 読み |

- 送信は 50 ms ちょうどで、データの書き換えは少し遅い（`sleep(0.05)` の後に処理が乗るため）
- 二つの周期がずれていくので、ときどき「前のフレームから書き換えが間に合わず、同じデータをもう一度送る」フレームが出る
- 計算上、書き換えの周期が約 51.9 ms なら 1 / (1/0.050 − 1/0.0519) ≒ **1.37 s ごと** に 1 回になり、実測の 1.35 s と合う（10-29 の 1.25 s は約 52.1 ms に当たる）
- 言い換えると、送られる車速の「古さ」が 0 → 50 ms へ 1.3 秒かけて少しずつ増え、同じ値を 2 回送った所で 0 に戻る（のこぎり形の遅れ）

## 4. 何が困るか

- ロボット側は、車速の差から加速度を見ている（DOB、局所の効きの当てはめ、加速度の判定など）。止まった周期はその場で加速度 0 に見え、約 1.3 秒ごとに加速度にとげが入る
- `ProblemReport_20261028.md` では、中速の減速中のブレーキの往復（B）の周期が約 1.35 s で、この跳ねとほぼ同じ周期だった。跳ねが往復を誘っている可能性はまだ消せていない
- 手順2 の学習データ（表を作る元）にも同じとげが入っている
- このあと予定している「新しい表への入れ替え」は、これを直してから行う（ユーザー決定 2026-10-28）

## 5. 直し方の候補（シミュレータ側）

| 案 | 内容 | 注意 |
|---|---|---|
| a | 送信データの書き換えを送信より細かくする（例: 10 ms ごと、または車速を計算するたびに `modify_data()`） | いちばん単純。BCM の 50 ms 送信はそのまま残るので、Python が止まってもフレームは途切れない |
| b | 書き換えのループを `sleep(0.05)` ではなく、絶対時刻で刻む（次の予定時刻まで待つ） | 平均の周期は 50 ms になるが、送信と位相が合わないと、まれに同じ値が出る可能性は残る |
| c | BCM をやめて、書き換えと送信を同じループで行う | Python が止まると送信も止まる（`4c361a4` で BCM にした理由に反する） |

推奨は **a**（「送るときにはいつも最新の車速が入っている」を作りで保証できるため）。

## 6. 直ったかの確かめ方

1. raspi3b 側で、CAN の送信ログ（`raspi3b_CAN_log.bat` など）から、同じデータのフレームが続く間隔を確かめる（直す前に、原因が 3. のとおりかもここで確かめる）
2. 直した後、ロボット側で 1 本走らせ（WLTP など）、2. と同じ数え方をする
   - 目安: 同じ値が来る回数が 0.90 回/s → ほぼ 0 になり、1.25〜1.35 s の周期の山が消えること（ロボットの周期のばらつき 31〜69 ms による、周期性のない少数の重なりは残りうる）
3. 合格したら、ProblemReport_20261028 の B（中速の減速中のブレーキの往復）が変わったかを見る

## 7. 結果（2026-10-29、ユーザーがシミュレータを修正）

修正前 `042914` と修正後 `052041` は同じ走り（Low・Mid、600 s）。2. と同じ数え方:

| | 修正前 `042914` | 修正後 `052041` |
|---|---|---|
| 加減速中の秒数 | 377 s | 376 s |
| 同じ値が来た回数 | 352 回（0.93 回/s） | **11 回（0.03 回/s）** |
| 間隔の山 | 1.1〜1.3 s に 172 回 | なし（176・208・228・253 s … とばらばら） |
| 1 周期の変化が約 0 の割合 | 7.0% | 2.7% |

- 残った 11 回は、どれも 90〜118 km/h でゆっくり加減速している所（0.5〜1.4 km/h/s、1 周期では 0.03〜0.07 km/h しか変わらない）。うち 2 回は、ロボットの周期が 31 ms／69 ms と乱れた所（同じフレームを 2 回読んだ）。周期性はない
- 判定: **約 1.3 秒ごとに止まる現象はなくなった**。B（中速の減速中のブレーキの往復）が変わったかは、5 モードの走りで別に見る
