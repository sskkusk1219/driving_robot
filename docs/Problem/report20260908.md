## 2. ILC の位相補償不足（① の主因）

Δplan（プラン更新量、走行 n→n+1 の `plan_effort_pct` 差分）と前走行の誤差 `e(t)=actual-ref` の相互相関を取ると、ピークが **lag +0.7〜+1.0秒**にある（本来は lag 0 であるべき）。

`plan_service.py:348`（旧実装）は先読み量に `Δ=fopdt_theta=0.30s` のみを使っており、プラント遅れ `tau=0.95s` が未補償だった。グラフ右上（t=90-145s の plan effort 反復推移）で、VERIFY→PLAN_LEARN#1 では改善しているが、PLAN_LEARN#2, #3 と反復するにつれて波形が高周波化・振幅増加しているのが確認できる。

実測での現れ方（t=114〜118s、55→64km/h を要求-2.0km/h/sで減速する区間）:
- 逆モデルの物理的に正しい値は **+3.2%**（FFサーフェスを直接評価して確認）
- ILC がこれを **0.0%** まで削り、代わりに t=110s を 5.0%→**14.4%** まで持ち上げていた
- PID トリムが ±9% 振って穴埋め → 偏差 -2.85km/h → +4.87km/h

plan_rms は VERIFY(10.43%)→PLAN_LEARN#3(11.32%) と単調増加、0.08-0.5Hz の振動成分も増加していた。

### 検証ツール

`scripts/replay_plan_update.py --cycle-id <id>` を新規作成した（読み取り専用・実機不要）。既存ログの連続走行ペアについて Δplan と誤差の相互相関の最良ラグを計算し、旧 Δ（theta のみ）・新 Δ（theta+tau）それぞれでの相関を比較できる。今回のサイクルで実行した結果、PLAN_LEARN の実走行ペア（967cefe7→6d2f140f, 6d2f140f→79222c72）では新 Δ の方が最良ラグに近い相関を示した。

## 3. 「best を採らない」設計と探索ノイズ（① の設計欠陥）

- `plan_learn.best_reward` は記録専用で、サイクル合否・完了メッセージには使われていなかった
- REFINE_FINAL の3本は**同一プラン**で走ったが p95 は 3.34/2.64/2.66 と ±0.7km/h ばらついた。1走行=1サンプルの評価では、この探索ノイズと「本当の悪化」を区別できていなかった

## 4. 誤差は減速区間に偏在（④、今回はスコープ外）

| 区間 | p95 | max |
|---|---|---|
| 加速（dref>+0.3） | **0.76** | 1.20 |
| 巡航（\|dref\|≤0.3） | 1.81 | 4.64 |
| 減速（dref<-0.3） | **3.41** | 4.88 |

実測の惰行減速は 20-70km/h帯で **-2.5〜-3.4km/h/s** だが、検証パターンの減速要求は **-2.0km/h/s**（グラフ左下）。つまり検証パターンの1/3程度が「惰行より緩い減速＝アクセルを踏みながら減速する」領域で、ここは FF・フェーズ分類・トリムの3者が最も噛み合いにくい。

学習運転（487秒）のデータ被覆を確認したところ、**中速域(30-70km/h)でアクセル5-15%を保持したデータがほぼ無い**（巡航トリムは1.5%/3.0%を8秒ずつ、110km/h域のみ）。

**今回のスコープ外とした理由**: これは制御ロジックの誤りではなく学習運転パターン・検証パターンの設計問題であり、変更には学習運転の開度スイープ設計（`src/domain/learning_drive.py`）とパターン生成（`src/domain/pid_tuning.py`）双方の再設計を要する。ユーザー確認により今回は「制御ループ是正＋サイクル構成の再編」に絞ったため、次回検討事項として記録する。

なお、逆モデル自体（2次多項式Ridge）は物理的に整合していることを確認済み（110km/h定常=3.6%↔実測惰行-1.5km/h/s、60km/h定常=13.1%↔実測惰行-3.1km/h/sと整合）。**モデル方式の変更は不要**と判断する。

## 5. 滑らかさ（②）

- アクセル開度の向き反転: 実測 **31〜33.5回/min**（2秒に1回）、ブレーキ 12〜18回/min
- applied effort 変化率 RMS: 7.0〜7.3%/s
- 車速には**フィルタが一切ない**（`can_reader.py` で生値素通し）。10Hz隣接差 std=0.205km/h がそのまま P/I 項に乗っていた
- 一方「アクセル⇔ブレーキ踏み替え」自体は 1.3回/min で許容内（目安≤2）→ 問題は踏み替えでなく**微小ハンチング**

ユーザー確認済みの滑らかさ合否目安（今回はKPIゲートに入れず記録・表示のみ）:
- ペダル向き反転 ≤10回/min
- 開度変化率 p95 ≤5%/s
- applied effort 変化率 RMS ≤3%/s

参考: 120km/h域での測定床は 0.5秒移動平均からの残差 p95=0.27km/h。p95≤0.4 に対し制御誤差に割ける予算は約0.30km/hで、達成可能だが余裕は大きくない。

## 6. 所要時間（③）

34.2分の内訳: 学習運転8.4分 / REFINE_1 3.3分 / VERIFY 3.2分 / PLAN_LEARN 9.6分 / REFINE_FINAL 9.6分。

REFINE_FINAL の9.6分は p95を3.34→2.66にしただけで、PLAN_LEARN #1の1.74より悪い状態で終わっており、**実質マイナスの9.6分**だった。

さらに検証パターン生成 (`pid_tuning.py::build_verification_trajectory`) の保持時間圧縮に既存のバグを発見した: 保持時間の床判定が `hold >= _VERIFY_STOP_HOLD_S(6.0)` となっており、通常の巡航保持（`_VERIFY_CRUISE_HOLD_S=7.0 >= 6.0`）まで誤って4秒の床に掛かっていた。このため `verify_pattern_budget_s` を180→130に下げても総尺は191.5秒のまま変わらなかった（本来の設計は最高速巡航≥10s・停止保持≥4sのみに床を置く意図）。この床判定を停止保持セグメント限定に修正し、budget_s が実際に効くようにした。

## 実施した修正

### Phase 1: ILC 位相補償
- `src/domain/control/plan_update.py`: `lead_time_from_fopdt(theta, tau)` を新設し `Δ=theta+tau_factor*tau`（`PLAN_LEAD_TAU_FACTOR=1.0`）に変更。`PLAN_L_GAIN_FACTOR` 0.4→0.25、`PLAN_UPDATE_CUTOFF_HZ` 0.3→0.2、`PLAN_DELTA_LIMIT_PCT` 10.0→4.0
- `src/app/plan_service.py`: `delta_s` の算出を新関数に差し替え
- 新規 `scripts/replay_plan_update.py`（読み取り専用の検証ツール）

### Phase 2: best 採用とロールバック
- `src/app/learning_cycle.py::_run_plan_learn_phase`: 各走行の reward・KPI を追跡し、**best 走行の KPI を最終結果として返す**（旧: 最終走行(last)）。明確な悪化（`PLAN_LEARN_DEGRADE_FACTOR=3.0`×epsilon 超）で即座に打ち切る `degraded` 判定を追加
- `src/app/plan_service.py::freeze_to_best` / `src/app/robot_controller.py::freeze_saved_plan_to_best`: PLAN_LEARN フェーズ終了時に保存プランを best_efforts へ明示的に確定
- `_kpi_passed` 等のドキュメント中「p95≤0.2」の記述を実定数 0.4 に修正（コメントの食い違いを解消）

### Phase 3: ばらつき対策・滑らかさ指標・車速フィルタ
- `src/domain/control/kpi_monitor.py`: `accel_reversals_per_min` / `brake_reversals_per_min` / `accel_rate_p95_pct_s` / `brake_rate_p95_pct_s` を追加（記録専用、KPIゲート対象外）
- `src/domain/control/reward.py`: `W_SMOOTH` 0.2→0.4（プラン学習の探索を滑らかさ側へ寄せる）
- `src/domain/control/drive_loop.py`: トリム／速い補正層PID入力にのみ実車速の0.25s 1次LPF (`SPEED_FEEDBACK_LPF_TAU_S`) を追加。KPI・ログ・ゲインスケジューリング・最小実効ブレーキ判定は生車速のまま

### Phase 4: サイクル構成の再編

| 段階 | 改善前 | 改善後 |
|---|---|---|
| 学習運転 | 8.4分 | 8.4分（スコープ外） |
| REFINE_1 | 66s×3 = 3.3分 | 66s×**2** = 2.2分 |
| VERIFY | 191s×1 = 3.2分 | **廃止** |

| REFINE_FINAL | 191s×3 = 9.6分 | **廃止** |

- `src/infra/settings.py::LearningSettings`: `refine_runs_stage1` 3→2、`verify_runs` 1→0、`verify_pattern_budget_s` 180→130、`plan_learn_runs_max` 8→4、`refine_final_runs` 3→0
- `src/domain/pid_tuning.py::build_verification_trajectory`: 保持時間の床判定バグを修正（`hold == _VERIFY_STOP_HOLD_S` に限定）。これにより budget_s が実際に効くようになり、1走行あたり 191.5s→155.5s に短縮（速度域の被覆は維持）

**時間目標について**: 最悪ケース（毎回 runs_max まで走る）で約21.0分となり、目標の20分をわずかに超える。ただし Phase 2 の早期打ち切り（KPI合格・明確な悪化）により実際の平均所要時間はこれより短くなる見込み。KPI優先の方針（ユーザー確認済み）により、この差は許容範囲と判断した。学習運転（8.4分）を含めた時間短縮には学習運転パターン自体の見直しが必要で、今回はスコープ外。

## 次回検討事項（今回スコープ外）

1. **学習運転パターンの再設計**: 中速域(30-70km/h)でのアクセル5-15%保持データを追加し、逆モデルの中速定常域を強化する
2. **検証・適合パターンの減速要求を惰行基準の相対値にする**: 現在は固定 -2.0km/h/s だが、実車の惰行減速カーブ（速度依存）を基準にした相対的な減速要求に変更することで、「アクセルを踏みながら減速する」領域を縮小できる可能性がある
3. Phase 4 の実施後、実機でサイクルを1回走らせて所要時間・KPI・滑らかさ指標を計測し、この分析の答え合わせをすること
